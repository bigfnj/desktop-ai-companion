AgentBroker guide

Setup

Enable AgentBroker in its settings pane. Its workstation MCP endpoint is http://127.0.0.1:7432/mcp, and the same listener answers http://localhost:7432/mcp. LAN HTTPS uses port 7433 by default.

The worker includes its runtime, so normal operation needs no ASP.NET installation and no administrator rights. Only the optional Windows Firewall setup action asks for administrator approval.

Discovery of open Codex and Claude sessions is on by default. Waking existing Codex sessions and waking existing Claude sessions are off by default; turn them on in Coding agents.

Connecting Claude Code and Codex

Connect MCP once per client for the receipt and reply tools. Connect Claude MCP and Connect Codex MCP add the user-scoped desktop-ai-companion-agentbroker entry through the client's own CLI. An existing entry is never silently replaced.

Claude Code uses the local HTTP endpoint when the connection needs no token; other connections use the stdio bridge. Client policy can require administrator approval: if registration is refused, ask the policy owner to approve the exact local server. AgentBroker does not override a policy refusal.

For Claude Code in VS Code, start a new conversation after connecting and check /mcp.

A session that started while the broker was down, including during a companion restart, has no broker tools until you reconnect its MCP server (Claude Code: /mcp) or restart the session.

The full-width Clients card shows one summary line per client: its name, a short headline, then a glyph for each state. A check mark means verified evidence, a warning or cross identifies a state or note to read. Each state that is not ok adds one line with its next step, and supplementary notes or a stored setup result (Last setup action) add lines too, so a healthy client is a single line only when it has neither. The card starts folded when no actionable warning or error remains. Publisher-verified update-tolerant delivery notes and owner-chosen wake-off or discovery-off states do not keep it open; configuration not checked, unattributed tools, an unregistered inbox, adapter errors and unknown or truncated notes do. The always-visible Clients line beside Pairing counts OK clients, notes and any clients whose native opt-in is off. The tray menu lists every state in full.

StateWhat it shows

Waking existing sessions

The Wake existing Codex sessions and Wake existing Claude sessions switches let messages reach existing idle client sessions automatically. MCP agents can still poll and reply without them.

For Claude, "Also wake updated Claude builds" (on by default) accepts a valid Anthropic signature on the running session's own executable for a build that is not exactly verified. Turn it off to wake exactly verified builds only.

For Codex, "Also wake updated Codex builds" (on by default) accepts a valid OpenAI signature plus the native capability checks for a build that is not exactly pinned. Turn it off to wake exactly verified builds only.

Claude wake-up uses sensitive local peer credentials. Existing agent permission controls still apply. Claude uses its peer-class token locally and never forwards it to another agent or workstation.

Watching the inbox during long background work (Claude Code)

Use the worker's --watch-inbox command through Claude Code's background-command mechanism for your own native address from whoami. It accepts only claude:<canonical lowercase GUID> session IDs, including the existing claude: prefix exactly once. Codex sessions and registered generic mcp: mailboxes use inbox reads at work milestones or incoming waits instead.

The command polls the exact address you supply. It exits 0 after a complete scan finds a pending, unexpired message whose ID is not in --seen-ids, after the supplied cursor or anywhere in the pending inbox when no cursor is supplied. It also ends on a time limit, parent loss, refusal or repeated scan failure. When the background command reports completion, inspect its metadata and read the inbox to handle the actual messages; completion alone does not establish mail or start any broker action.

  1. First read your inbox with read_inbox_page until hasMore is false. Keep the content, handle each message, and acknowledge it when you are permitted to. Keep the last nextCursor if you have one. Put at most 64 handled message IDs that may still read pending in $seenIds below, as canonical lowercase GUIDs separated by commas with no spaces. The recipe omits --seen-ids automatically when that value is empty. Arming never requires acknowledging anything.
  2. Find your Claude Code host process and its creation time as a Windows FILETIME. Save these lines as a .ps1 file and run it with powershell.exe -NoProfile -ExecutionPolicy Bypass -File on that file. Do not paste them into Git Bash inside double quotes: bash would expand the $ signs first. 
    $p = Get-CimInstance Win32_Process -Filter "ProcessId=$PID"
for ($i = 0; $p -and $p.Name -ne 'claude.exe' -and $i -lt 32; $i++) {
    if ($p.ParentProcessId -eq 0 -or $p.ParentProcessId -eq $p.ProcessId) { $p = $null; break }
    $p = Get-CimInstance Win32_Process -Filter "ProcessId=$($p.ParentProcessId)"
}
if (-not $p -or $p.Name -ne 'claude.exe') { throw 'No claude.exe ancestor: use --unbound with a finite --max-seconds instead.' }
"$($p.ProcessId) $((Get-Process -Id $p.ProcessId).StartTime.ToUniversalTime().ToFileTimeUtc())"
    It prints the PID and the FILETIME (100-nanosecond intervals since 1601). Do not use a .NET DateTime's Ticks, which count from year 1.
  3. Write the watcher command as a .ps1 file, replacing every value in angle brackets with your exact values; copy GUIDs in canonical lowercase form. Start it as a background command (in Claude Code, a Bash command with run_in_background that runs powershell.exe -NoProfile -ExecutionPolicy Bypass -File on that file; without -ExecutionPolicy Bypass, the default Windows policy refuses an unsigned script before it starts and no line is printed). The worker and data paths below are for a default per-user install; use yours if they differ. A portable copy keeps this module's data in data\modules\agentbroker and its worker in modules\agentbroker\worker\AgentBroker.Worker.exe, both beside the companion executable. The arm root is a separate directory you choose, not an installation path; this example creates it before use. 
    $worker = Join-Path $env:LOCALAPPDATA 'Programs\Desktop AI Companion\modules\agentbroker\worker\AgentBroker.Worker.exe'
$armRoot = Join-Path $env:LOCALAPPDATA 'AgentBrokerWatch'
$null = New-Item -ItemType Directory -Force -Path $armRoot
$cursor = '' # Paste the last nextCursor here when available.
$seenIds = '' # At most 64 canonical lowercase GUIDs, comma-separated with no spaces.
$watchArgs = @(
    '--watch-inbox',
    '--data', (Join-Path $env:LOCALAPPDATA 'DesktopAICompanion\modules\agentbroker'),
    '--broker-id', '<broker ID>',
    '--session-id', '<sessionId from whoami, which already starts with claude:>',
    '--incarnation', '<incarnation>',
    '--arm-root', $armRoot,
    '--max-seconds', '7200',
    '--parent-pid', '<PID>',
    '--parent-start', '<FILETIME>'
)
if ($cursor) { $watchArgs += '--cursor', $cursor }
if ($seenIds) { $watchArgs += '--seen-ids', $seenIds }
& $worker @watchArgs
exit $LASTEXITCODE
    Never pass an empty value. The worker refuses an empty --cursor on any shell, and Windows PowerShell 5.1 drops an empty native argument. The conditional additions omit the --cursor pair when you have no cursor and the --seen-ids pair when you handled no IDs; leave the corresponding variable empty instead of editing the argument array. Use your exact address from whoami: its brokerId, its sessionId exactly as printed (it already starts with claude:, so do not add another) and its incarnation. --max-seconds is required: choose a finite lifetime from 1 through 31,536,000 seconds. If no host process can be named, replace the two parent options with --unbound; it still needs --max-seconds and does not watch the host.
  4. Keep the same arm root, --data directory and exact address (broker ID, session ID and incarnation) across runs. While that lock is held, another process opening the same lock is refused with exit 25; different arm roots do not coordinate. The arm root must exist, use a canonical drive-letter absolute path with no trailing separator, and have no junction or symbolic link in its path. The data directory must also exist and use a canonical drive-letter absolute path with no trailing separator. --interval-seconds sets the pause after each scan: default 15, range 1 through 300 seconds, shortened to the remaining lifetime. Each authenticated inbox call is bounded by the smaller of 40 seconds and the remaining lifetime, or ends earlier when parent monitoring cancels it.
  5. When the command ends normally it prints one line of fixed metadata, never message text, and nothing is ever acknowledged. Use this table to decide what to do next:
    ExitMeaning and next step
    0Unseen pending mail: a complete scan found an ID not in --seen-ids. Read, retain and handle the messages. If work continues, rearm with the cursor from that read and any handled IDs still pending. The metadata line contains no cursor.
    20The finite lifetime ended (lifetime) or the watch was cancelled (cancelled), for example after a parent-monitoring failure while the parent was still running. If unreported is greater than 0, read the inbox before deciding whether to rearm.
    21read_inbox_page refused: session_unavailable, invalid_inbox_cursor or another tool_error. Verify your full address with whoami and read the inbox from the start for a fresh cursor. If the exact address is still unavailable, wait for current discovery; do not rearm with the old address.
    22Four scans in a row failed. Read the inbox and check the broker before starting again.
    23The parent named by --parent-pid and --parent-start ended or could no longer be confirmed as that exact process. This applies only in bound mode; a parent already unconfirmed at arming produces exit 2.
    24The broker reopened its inbox after a worker restart or an in-process certificate-renewal reload, invalidating the cursor. Discard it, read the whole inbox, handle each message ID once, then rearm with the cursor from that read.
    25The lock for this arm root, data directory and exact address is already held by another watcher or another process. Different roots do not share this lock.
    2Arming was refused before watching began: invalid arguments, an unconfirmed parent, missing or unusable data/arm directories, or another pre-arm setup failure. Read the inbox, then review the command before rearming.
    26An internal or output failure. It can occur before or during watching, and an output failure may hide mail already found. Read the inbox, then review the command before rearming.

    If unreported is greater than 0, a partial scan validated unseen IDs it could not report as a complete scan; read the inbox before anything else. A value of 0 does not mean the inbox is empty. A run that ends without a complete metadata line establishes neither mail nor an empty inbox; read the inbox before deciding whether to rearm. These incomplete or failed outcomes never mean mail.

When the session is idle, the broker may also deliver the same message directly, so you can be told about one message twice; handle each message ID once.

Pairing brokers

Pairing happens in the pane's Brokers list or from the tray submenu, with no popup. The list's groups are Awaiting approval (listed first), Discovered and Paired. Paired and Discovered rows start with the first 8 characters of the broker's ID, then its name, so two brokers with one name stay apart. An Awaiting approval row shows the broker's name, but its complete code leaves little room, so a long name is shortened: a default computer name such as DESKTOP-7Q2K9LM shows only as "DESKTOP-…". Give each workstation a short Broker name (under Connections) before pairing. In the list, tick exactly one broker, then press Request pairing, Codes match: approve, Cancel pairing or Revoke sharing.

An Awaiting approval row's detail is the complete comparison code. Pairing names each waiting request by name and the same ID, with its direction and expiry, and states the sharing scope before you approve. Approve on both workstations only after the codes match. A request or a single approval grants no sharing. Pairing shares both brokers' current and future discoverable sessions. Mark a session private to hide it, or mute it to stop peer messages. LAN connections always authenticate.

Revoke sharing acts on the second press within 15 seconds. It is in the pane only, never in the tray, so removing a pairing is always deliberate. The list changes only when the pane is rebuilt, so press Refresh brokers to update it. A waiting incoming request also shows in Pairing and in the tray label "AgentBroker: pairing request waiting".

If multicast discovery is blocked, use Copy my invitation on one workstation, copy that public invitation to the other workstation's clipboard and press Pair from copied invitation in its Brokers card. The first press previews the broker's name, short ID and endpoint authority without sending a request or echoing clipboard text. Check that identity, then press the same button again within 30 seconds to request pairing. A changed or expired preview needs a new first press. The broker refuses its own invitation and an identity it has already paired. Complete the same code approval on both workstations. Invitations contain public identity information only.

Both workstations must reach the HTTPS port, and automatic discovery also needs UDP 5353 on the local network. Allow LAN access asks for consent and then Windows administrator approval. It adds an inbound rule for the worker and its TCP port, limited to Private networks and the local subnet, and never a Public-network rule.

Mail that is waiting

A message stays pending in its recipient's inbox until the recipient acknowledges it, an eligible fresh local reply settles it, or its deadline passes. An agent waits for mail with wait_for_messages, or fetches it during active work with read_inbox_page, which does not block. Reading acknowledges nothing: retain the content before acknowledging or replying.

A fresh reply_to_message records Delivered with reason reply_receipt and removes its parent's text only when both peers are local, the recipient's current row has Receive, and the unexpired parent is Accepted, Submitting, Submitted or Uncertain. A retry of an existing reply, a reply to a paired broker, or a reply to Held leaves that parent's receipt unchanged. If the reply did not settle it, acknowledge Delivered explicitly when permitted. To keep the broker's text, acknowledge Held before replying, then mark Delivered before the original deadline; Held does not extend it. Delivered means receipt, not completion of the requested work.

A sender learns what happened through wait_for_receipt or get_message_receipt. Accepted and Submitted are not Delivered. A message to a native session that has not been tried yet names why it waits, for example recipient_busy.

The Default message delivery window applies to new replies and sends using ttlMinutes 0; explicit message deadlines stay unchanged. Delivered remains Delivered after its original delivery deadline; reading alone does not acknowledge; Held keeps the text without extending its deadline. A generic mailbox stays addressable for 24 hours after its owner's last call, as long as the agent keeps the same clientId and incarnation.

A mailbox stays listed to paired brokers only while its owner calls at least every 50 seconds; back-to-back 25-second wait_for_messages calls do that. One call every 180 seconds lists it for 60 of each 180 seconds, and it still receives while it is not listed.

The pane's Waiting mail row lists each registered session on this workstation that has messages still pending, with how many of them are still queued (Accepted) and how many of those wait while the session is busy. Pending also covers Submitting, Submitted and Uncertain messages, so the three counts are separate and none of them is Delivered. Sessions with nothing pending are left out. "No messages waiting for registered sessions." means the worker reported none for the sessions registered now; mail kept for an address that is no longer registered is not counted.

The busy time is the worker's own measurement: a process-local observed lower bound; resets on worker restart. When it reaches the worker's sender notice threshold (5 minutes in this version), the row says so. The worker then sends at most one advisory per message, and only to a sender on this workstation once that sender can take it; a sender on a paired broker gets none from this worker. The pane raises no popup or question. While mail for a registered session has waited past that threshold, Status and the tray's AgentBroker label also say mail is waiting for a busy session, and both clear when that no longer holds.

"Measurement unavailable" means the worker did not report waiting mail: a worker without this measurement, a failed read, or an answer from another broker. It never means zero, and the rest of the pane is unaffected.

Troubleshooting

  • A session has no broker tools: reconnect its MCP server (Claude Code: /mcp) or restart the session.
  • Configuration absent: use Connect Claude MCP or Connect Codex MCP. Not checked: choose Check client setup.
  • Blocked by managed policy: ask the policy owner to approve this exact local server.
  • CLI not found: the companion starts claude.exe or codex.exe itself and never runs a script shim such as claude.cmd.
  • Inbox none registered: an agent registers with register_agent; an MCP connection alone is not an inbox.
  • Native wake off: turn on Wake existing Claude sessions or Wake existing Codex sessions.
  • An elevated session cannot be woken: use register_agent or run the session unelevated.
  • Other PCs cannot connect: check LAN firewall access. A Public or Domain network with a rule for Private networks only explains it.
  • A pairing result was lost: refresh the Brokers list and look at Awaiting approval and Paired before retrying. A timed-out reply does not prove that nothing changed.
