# AgentBroker implementation and validation

AgentBroker adds local MCP messaging and paired LAN brokers through a separate, self-contained worker. Native GUI delivery is explicitly enabled and subject to client compatibility and publisher-trust checks. The evidence below distinguishes automated checks from live GUI acceptance.

The [campaign validation and disposition record](agentbroker-180-validation.md) tracks the initial 1.8.0 publication, the subsequent 1.9.0 repairs, their tests and explicit acceptance limits.

## Setup

Install AgentBroker from the module catalog, then enable it in its options pane. Its workstation MCP endpoint is `http://127.0.0.1:7432/mcp`; the same listener answers `http://localhost:7432/mcp`. LAN HTTPS uses port 7433 by default. The worker includes its runtime, so normal operation does not require an ASP.NET installation or administrator privileges. The optional Windows Firewall setup action requires administrator approval.

Use **Connect Codex MCP** or **Connect Claude MCP** in the module options to add the named, user-scoped `desktop-ai-companion-agentbroker` entry through the vendor CLI. Existing entries are never silently replaced. Claude Code prefers the broker's live loopback HTTP endpoint when the user-only management connection confirms that no token is required. Newly added Codex entries use the stdio bridge, which retrieves its current connection through that pipe; Claude Code also uses that bridge for a verified token-required connection. An existing Codex HTTP entry is recognized only when its loopback URL matches this broker's verified live, token-free control connection. Token-required HTTP entries remain unchanged for connection review. If the live control connection is unavailable or unverified, an HTTP entry whose URL is exactly `http://127.0.0.1:<port>/mcp` or `http://localhost:<port>/mcp` is reported as not verified; refresh status, then choose Check client setup again. Any other HTTP entry stays an entry that needs review. If Connect Claude MCP stops at connection verification in the current run, no vendor CLI starts and Last setup action records the refresh guidance. Neither route persists a broker access token in client configuration. The buttons find each CLI the way the companion's model calls do: on PATH, where an npm shim counts as the binary it starts and that binary is run directly, never the shim or cmd.exe; then the PATH saved for new terminals, npm's default prefix, Claude Code's own installer, WinGet's package folders, and last the copy inside VS Code's Claude Code extension. The located binary starts once. A failing CLI is never followed by another candidate, and PATH is never changed.

**Connect Claude MCP** configures Claude Code, including its VS Code extension. After successful registration, start a new Claude conversation and check `/mcp`; reloading VS Code is not normally necessary. Managed policy can allow HTTP URLs separately from stdio commands, and a loopback URL still needs approval when an allowlist is enforced. When the allowlist refuses the `http://127.0.0.1:<port>/mcp` URL (`not allowed by enterprise policy`), the button adds `http://localhost:<port>/mcp` once more, the same listener under the name a policy can admit as `serverUrl` `http://localhost*`. If registration is still refused, ask the policy owner to approve one of those exact local server URLs or the stdio command and arguments, as applicable, or deploy the approved server through managed configuration. An explicit deny and every other failure are final: AgentBroker does not retry another transport or override policy after a refusal. See [Claude's managed MCP documentation](https://code.claude.com/docs/en/managed-mcp).

An organization can delegate a soft allowlist that people may extend in their own settings. In that case, the reviewed `tools/agentbroker/Grant-ClaudeLocalMcpAllowance.ps1` helper can append only the exact local AgentBroker URL after an explicit approved action. It retains a private rollback copy and does not change managed files, policy locks, denials or server definitions. Managed restrictions still apply, and the normal vendor CLI remains the final authority. A locked allowlist or other refusal requires the policy owner's action.

Registration confirms that the server definition was saved. Connection additionally requires an MCP handshake and a usable tool list. The reviewed `Connect-ClaudeMcpEntry.mjs --verify-http` mode checks only the fixed AgentBroker name and exact local HTTP entry, then reports fixed status fields without forwarding CLI diagnostics, headers or configuration. It runs no model or native wake command. A successful CLI check proves that CLI connection; a normally opened VS Code conversation must still load the entry and show it connected in `/mcp`.

Since 1.10.5 the pane keeps each explanation to one or two sentences. **Open the AgentBroker guide** copies an offline guide, embedded in the module DLL, into a `guide` folder in module storage and asks Windows to open that copy; it refuses a folder that is a link or lies outside storage, works without a network and always matches the installed version (`AgentBrokerModule.Guide.cs`, `Guide/agentbroker-guide.html`). The consent that Claude wake-up uses sensitive local peer credentials stays in the pane, in the row directly under **Wake existing Claude sessions**.

Metadata discovery defaults on. Native Codex peer delivery and Claude peer credential access default off. Enable a native adapter only after reviewing its [compatibility requirements](agentbroker-client-compatibility.md). Claude uses its peer-class token locally and delegates inbound acceptance, holding and refusal to the recipient's own policy. It never forwards that credential to another agent or workstation.

The **Wake existing Codex sessions** and **Wake existing Claude sessions** switches enable automatic delivery into normally opened idle client sessions. They are needed for that behavior. MCP discovery, inbox polling and replies work without native wake, so the switches are separate opt-ins. Beneath each, **Also wake updated Codex builds** and **Also wake updated Claude builds** (both on by default; Claude's since the owner's decision of 2026-11-02) let a client build that is not exactly pinned be woken when Windows verifies its publisher's signature, so a client's own update does not stop wake-ups until a re-pin ships; off keeps exact pins only (`docs/agentbroker-client-compatibility.md`, "Update-tolerant native delivery contract"). Host 1.6.1 and module 1.0.2 refresh status in place without resetting pending edits; a worker that misses its startup deadline reports an unavailable state rather than remaining indefinitely at Starting.

### MCP connection status

Module 1.0.3 added MCP endpoint readiness and Claude/Codex last-seen activity. **Status** now carries the readiness summary, such as `MCP ready.`, while **MCP client traffic** carries details such as `Claude client: seen just now` and `Codex client: not seen`. Only successful MCP traffic counts. Saved client configuration and discovered native sessions do not establish an MCP connection.

HTTP clients connect on demand, so an idle client does not become disconnected after an arbitrary timeout. Last seen means successful traffic observed since this worker started; observations reset on worker restart. A client can still display a cached connection before it sends its next request. Older stateless tool requests omit client identity and appear under Other clients; initialization or supported per-request identity supplies the Claude/Codex label. Labels are self-reported display information and grant no access.

These observations retain only three fixed client categories and timestamps, plus the address of each generic inbox whose own `register_agent` request identified its client. Status uses the existing refresh cycle, without launching vendor commands, sending agent messages or storing request contents. Disabled, unavailable and older workers without MCP status are shown explicitly.

### Client setup states

The full-width **Clients** card has one row for Claude Code, whose CLI and VS Code extension share one configuration, and one row for Codex. Since 1.10.5 each row starts with one summary line: the client's name, its headline, then a glyph and a short name for each state below, such as `wake 3/3`. A state that is not ok adds one line of its own with its next step, and supplementary notes or a stored setup result (Last setup action) add lines too, so a healthy client is a single line only when it has neither; a Tools warning also says how to reconnect (`/mcp` for Claude Code, a session restart for Codex). The card starts folded when no actionable warning or error remains. Publisher-verified update-tolerant delivery notes and owner-chosen wake-off or discovery-off states do not keep it open; configuration not checked, unattributed tools, an unregistered inbox, adapter errors and unknown or truncated notes do. The always-visible Clients line beside Pairing counts OK clients, notes and clients whose native opt-in is off. The tray carries the same rows as one item per client, with every state as its own sentence (`AgentBrokerModule.Clients.cs`). Each state in a row comes from its own evidence:

| State | Evidence |
|---|---|
| Broker | The worker's status: running, running in another companion (standby), or not running. |
| Configuration | **Check client setup** runs the client's read-only `mcp get` for the `desktop-ai-companion-agentbroker` entry only: `claude mcp get <name>` or `codex mcp get <name> --json`. It reports an entry that matches this broker's supported connection with its effective scope and transport, an absent entry, an entry under that name that needs connection review, an HTTP entry not verified because the live broker connection is unavailable, an entry the client reports rejected or disabled, a managed-policy refusal, a CLI that was not found, or a report this version does not recognize. | Native | The client's discovery and wake switches, its adapter's reported errors and its discovered native sessions. |

The configuration check runs only when asked: from the pane, from the tray, or after **Connect Claude MCP** or **Connect Codex MCP**. The two-second status poll never starts a vendor CLI. Claude's `mcp get` makes its own connection to the configured entry, which is why the Claude row can report the endpoint reachable. The check never reads or writes a client configuration file and shows fixed states only, never CLI output. A settings change clears the previous check, because it compared the entry with the old port and paths. The companion finds `claude.exe` or `codex.exe` by the same rules as its model calls (see Setup) and starts that binary itself. An npm `claude.cmd` or `codex.cmd` shim is never run, only resolved to the binary it would start; CLI not found means no rung of that order holds the client. The tray item for a client whose entry is absent also offers its Connect action.

If settings change while a setup action is running, that old action cannot update the new connection's cached status or notifications. If its action row remains on screen, as it can after a settings change from the tray, the row shows the sanitized result and asks for another check. Applying settings from this pane rebuilds it and discards an in-flight action's row and result. Run **Check client setup** before deciding whether to retry.

### Pairing and deadlines

Since 1.10.5, pairing happens in the pane's **Brokers** list, with no popup. Its groups are **Awaiting approval** (listed first), **Discovered** and **Paired**. Paired and Discovered rows start with the first 8 characters of the broker's ID, then its name. An Awaiting approval row shows the broker's name, and its detail is the complete comparison code and nothing else. The code leaves the name about 50 to 75 DIP, so a long name ends in an ellipsis: a default computer name such as DESKTOP-7Q2K9LM shows only its first eight or so characters, while a short **Broker name** set before pairing reads in full. A request whose certificate differs from a paired one leads its row with a warning sign. Tick exactly one broker, then press **Request pairing**, **Codes match: approve**, **Cancel pairing** or **Revoke sharing**. **Pairing** names each waiting request by name and the same ID, with its direction and expiry, and states the sharing scope before either workstation approves. A request that uses a paired broker's ID with a different certificate is marked, and it cannot complete while that pairing is saved. Approve on both workstations only after the codes match. A request or a single approval grants no sharing. Pairing authorizes both brokers' current and future discoverable sessions. **Revoke sharing** acts on the second press within 15 seconds. The list changes only when the pane is rebuilt, so press **Refresh brokers** to update it. A waiting incoming request also shows in **Pairing** and in the tray label "AgentBroker: pairing request waiting". The tray keeps its pairing, private and mute controls. Revoking sharing is in the pane only, so it always takes the two deliberate presses.

The same **Brokers** card contains **Copy my invitation** and **Pair from copied invitation**. If multicast discovery is blocked, copy the public invitation on one workstation to the other's clipboard. The first **Pair from copied invitation** press previews only the sanitized broker name, short ID and HTTPS endpoint authority, without echoing clipboard contents or sending a request. The second press within 30 seconds confirms that same invitation and requests pairing; a changed or expired preview needs a new first press. This broker's own invitation and an already-paired identity are refused. Complete the same code approval on both workstations. Invitations contain public identity information only; there is no separate invitation card.

When pending mail has been observed waiting while a session is busy for at least the worker's notice threshold, **Status** points to **Waiting mail** and the tray label adds "mail waiting for a busy session" or a session count. Status retains the core/MCP status, existing pairing errors and dropped-notice diagnostics; the tray combines the waiting-mail hint with its incoming-pairing signal. The age remains in Waiting mail. Both signals clear when a status refresh or module state change removes that qualifying condition; the tray reads its label when its menu opens.

Simultaneous requests previously left two offers with different comparison codes on each broker. A deterministic HTTPS regression reproduced that failure before the fix. A collision now keeps the lower broker identity's outbound offer and retires the other request, nonce and code. Repeated requests for an exact pending peer reuse its current offer. Both users must still approve the same complete code; approval of a discarded code never transfers. A Brokers row bound to a replaced offer cannot approve the new one; press **Refresh brokers** and compare the new code. A collision displays current-code guidance rather than a connection failure, with no automatic retry or authorization.

Pairing requests and confirmations use a 30-second control-client deadline around the worker's 25-second operation deadline. A request can perform two HTTPS exchanges, each bounded to ten seconds. Ordinary status retains its three-second client deadline. Network, TLS and rejected-offer failures remain visible in the Pairing information, tray and pinned failure status after healthy status polls. A saved pairing for the same broker ID and certificate clears its obsolete pairing failure, while errors for other identities remain. The pane and tray show saved trust separately from current reachability. Guidance uses fixed error categories without raw remote diagnostics. If a result is lost, inspect pending or paired brokers before retrying; a timed-out reply does not prove that no state changed.

The pinned **Pairing** row reports the pairing state, clock warnings and the 32-broker limit notice. While AgentBroker is enabled but has no current worker snapshot, it reports paired-broker status unavailable alongside any retained pairing result. The **Brokers** card shows saved pairings alongside requests and discovered identities. Saved trust does not establish current reachability. A successful pairing remains visible after restarting the worker; delayed status responses cannot replace a newer pairing or revocation observation.

Both workstations must be able to reach the configured HTTPS port. Automatic discovery also needs UDP 5353 on the local network. In the AgentBroker settings pane or tray menu, choose **Allow LAN access** after this companion's own LAN worker reaches Running. The companion asks for consent, then requests Windows administrator approval. Its fixed-purpose worker command adds an inbound allow rule for that exact executable and applied TCP port, limited to the Private profile and LocalSubnet, with edge traversal disabled. It adds no Public-network rule, changes no existing rules and configures no router port forwarding. Run the action on each workstation that needs inbound access. Changing the applied port or installation path needs another setup action; previous rules are not removed automatically.

Setup verifies the requested rule and reuses an identical existing rule. Conflicting rules, possible application block rules and policy restrictions are reported for review rather than edited. An allow rule alone does not prove reachability: other firewall rules or network policy can still block the connection. A timed-out or interrupted Windows setup has an unconfirmed outcome, and another action waits for the original elevation operation to finish. The management pipe remains local, and pairing still requires both brokers' explicit approval. A physical second-workstation test remains necessary to validate a particular LAN's routing and firewall configuration.

**LAN firewall access** also shows three separate readings. The network category (Public, Private or Domain) is the one Windows applies to the interface carrying the broker's advertised LAN address, read through Network List Manager without administrator rights. The firewall rule state is this worker's own rule as Windows Firewall lists it: configured for the Private profile, absent, or a different rule under its name. When the network is Public or Domain and the rule covers Private networks only, one sentence explains why other PCs cannot connect. AgentBroker never changes a network category and never adds a Public-network rule. **Observed** says whether an HTTPS request from another private address has reached the LAN listener since the worker started. A configured rule is not observed reachability, and a request from this PC to its own address does not count. The category and rule are read in the background and reused for a short interval (`LanProfileMonitor.MaximumAge`), so a status request never waits for them.

Discovery checks private IPv4 interfaces every ten seconds, retries while offline, and recreates sockets after interface changes or transport failures. Pairing survives worker restarts and reboots when each broker keeps its Windows user, data directory and identity. A paired broker keeps using its saved address while that address works. If discovery announces a changed private IPv4 HTTPS address, automatic recovery verifies the original broker ID and paired public identity over HTTPS before saving the new endpoint. The original approval, identity pin and name remain unchanged. Since 1.9.0, a renewed TLS certificate can prove continuity with that original pin using the same private key. Discovery cannot create trust or restore a revoked pairing; a replaced identity requires explicit pairing again.

A read-only LAN probe successfully reached a discovered peer's pinned HTTPS public-info endpoint without pairing approval or agent input. Later historical physical two-workstation tests passed message delivery, acknowledgement and correlated replies on 2026-11-02; Claude native wake and its reply also crossed the pairing. The dated receipts are retained under `N-agentbroker-two-pc-01` in [BLOCKED.md](BLOCKED.md) and in the [1.8.0 wake-subpoint record](agentbroker-180-validation.md#wake-subpoints-and-backlog-burn-down-audit). These successes do not establish every physical restart, reboot, DHCP or revocation case, or repeat acceptance for the current package. The synthetic HTTPS collision smoke and full network regression remain separate evidence.

## Agent tools

The MCP server exposes `whoami`, `register_agent`, `list_sessions`, `send`, `wait_for_receipt`, `wait_for_reply`, `wait_for_messages`, `acknowledge_message`, `reply_to_message`, `read_inbox`, `read_inbox_page`, `read_native_recovery`, `set_session_declaration`, `set_session_title`, `get_message_receipt`, `send_message` and, since 1.10.5, `send_with_attachments` and `fetch_attachment` (see File attachments below). Every `initialize` result carries the short instructions card in `BrokerInstructions.cs`, forwarded unchanged by the stdio bridge. Use complete addresses and stable message IDs. A native submission is not proof that the recipient received it; explicit acknowledgement remains separate from work completion.

The optional [Claude custom-title hook](agentbroker-claude-title-hook.md) adds documented custom titles to local directory rows. Generated titles are unavailable through that hook. Titles and manual declarations are display hints; neither changes an address, grants predecessor rights, or reaches a paired broker.

### Receiving during active work

`read_inbox_page(session, cursor, limit)` fetches pending messages without blocking or taking a wait slot. It works on the existing exact native address while its turn remains active; it does not inject into that turn, create a mailbox, or start a background poller. `limit` defaults to 16 and must be 1 through 16. Each `entries` element contains an `arrivalSequence` and a complete `receipt`. The result also contains `pendingCount`, `hasMore`, and `nextCursor`. Pending means an unexpired incoming message still `Accepted`, `Submitting`, `Submitted`, or `Uncertain`; `Held`, `Delivered`, and `Refused` are already acknowledged and omitted. Reading acknowledges nothing. Retain content before acknowledging or replying: a fresh `reply_to_message` also records `Delivered` with reason `reply_receipt` for an unexpired pending parent when both peers are local and the recipient's current row has `Receive`, removing its text atomically with the reply. Other replies leave the parent unchanged. If a reply did not settle the parent, acknowledge `Delivered` when permitted. To keep text, acknowledge `Held` before replying, then `Delivered` when done. Held does not extend the original deadline; mark `Delivered` before it expires. A reply does not settle `Held`. Handle each message ID once if wake or another fetch also supplies it.

Start without a cursor, retain each page's content, and continue with its opaque `nextCursor`. Unlike the legacy `read_inbox` GUID cursor, this cursor can be retained between polls: new arrivals receive larger broker-assigned sequences, even when their UUID or sender-supplied creation time sorts earlier. `pendingCount` counts all pending messages for the address, including earlier arrivals already passed by the cursor. An empty incremental page can therefore have a positive pending count. Start again without a cursor when those earlier messages need rereading.

The sequence index lives only for one worker opening and is rebuilt from the durable snapshot's acceptance order. `inbox_cursor_reset_required` means the worker restarted: discard the cursor, rescan without one, and deduplicate by message ID. `invalid_inbox_cursor` refuses malformed, unsupported, wrong-address, or future cursors. `session_unavailable` requires refreshing native discovery, or re-registering the same generic mailbox identity. No cursor adds ownership or recovery rights across incarnations. Legacy `read_inbox` retains its history ordering, and schema-1 persistence is unchanged (`src/AgentBroker.Core/PendingInbox.cs`). Since 1.10.0, MCP inbox, incoming-wait and acknowledgement responses explicitly include `replyTo: null` for non-reply `BrokerMessage` values. Recovery entries also include `blockReason: null` when unblocked. This additive null output follows the published required-nullable schema; durable and federation serializers are unchanged (`McpToolJson.cs`).

Successful local operations that establish an exact participant append an `agentbroker.pending_messages` JSON advisory after their existing content blocks. It supplies the exact `session`, `status`, `pendingCount`, and `fetchTool`. The original first block stays unchanged; `send` keeps its existing generic-mailbox advisory too. An unavailable count is explicitly `status: unavailable` with `pendingCount: null`, never zero. A shared Codex transport cannot identify one chat, so operations with no unambiguous participant, such as `list_sessions` and `get_message_receipt`, receive no session-specific hint. The hint is a fresh observation after the operation, so concurrent arrivals can make it newer than the operation's own result (`BrokerTools.Inbox.cs`, `McpActivityTracker.cs`).

### Native session recovery

`read_native_recovery(session, cursor, limit)` inventories the retained incoming and outgoing records of the current native conversation, including earlier incarnations. The current address must have been observed by its matching `claude-native` or `codex-native` adapter, must still have that discovery lease, and must support receiving. A generic registration, matching label, native-looking ID, or direct registration cannot establish this authority. Local access remains broker-scoped; this feature does not authenticate which Codex chat owns a shared client connection (`NativeRecovery.cs`, `BrokerRuntime.cs`).

Each entry preserves the original receipt, sender, recipient, message ID, conversation ID and `replyTo`. It reports the incoming/outgoing relationship, earlier incarnations and retained-content availability. `canAcknowledge` and `canReply` describe ordinary operations for the current exact recipient only; both are false for a predecessor's records. Acknowledged tombstones retain metadata without their original text. Current privacy and revoked peer trust suppress peer content and actions.

The opaque cursor orders records when the local inventory first observes them; it does not reconstruct historical arrival order for tombstones. It can continue to newly observed records between calls. Start without a cursor to refresh changed statuses, availability and action fields of records already seen. A worker restart or privacy/trust policy change explicitly returns `native_recovery_cursor_reset_required`; discard the cursor and rescan. Queries are bounded to 1 through 16 entries, and recovery indexing is lazy on explicit inventory reads rather than scanning tombstones on each ordinary commit.

Recovery is report-only. A successor cannot acknowledge, reply as, or reactivate its predecessor. After inspecting retained content and receipts, an authorized agent may continue with an explicit new `send` between current complete addresses, using a fresh message ID and a conversation reference when useful. Recovery does not grant permission to repeat an old task.

New sends and replies still require an addressable exact recipient. The broker does not hold a new reply for an absent native requester or route it to a successor. When fresh matching native discovery proves a replacement incarnation, delivery re-evaluation refuses its predecessor's never-submitted Accepted mail as `recipient_replaced` and uses the existing exact-sender notice path. A lease lapse alone does not establish replacement. Submitting, Submitted and Uncertain mail is preserved because it may have reached native input.

Fresh verified native calls receive `recoveryPendingCount` and `recoveryTool` in their pending advisory. That count describes pending incoming messages addressed to earlier incarnations, not the whole retained recovery inventory or any action rights. Recovery has no automatic wake; the current native session calls explicitly. No payload is retargeted or uncertain submission reinjected. Inbox and recovery tools publish output schemas and `structuredContent` while preserving complete JSON in `content[0]`.

### Advisory blocks

A tool result's first content block, `content[0]`, holds the tool's own result: the returned value, or the SDK's error text when the call failed. `read_inbox_page` and `read_native_recovery` also return that value as `structuredContent`. Every later block is advisory; read the result from `content[0]` or `structuredContent`, never from a later block. A later block is either a JSON object, one per text block, with a string member `kind` in the `agentbroker.*` namespace, or plain text. Today the only plain-text later block is the generic-mailbox advisory that `send` and `send_with_attachments` can add as their second block (see Sending; `BrokerTools.SendAdvisory`). This release emits two JSON kinds, each at most once per result, and only to callers on this workstation's loopback endpoint; a paired broker's caller receives neither (`McpActivityFilters.LocalContext`).

- `agentbroker.recovery_guidance` holds a `guidance` object with `code`, `nextTool`, `advice` and `deliveryMayHaveOccurred`; on a failed call it can also name the `operation` and an `availability` diagnostic. It follows the error text of a failed call whose refusal code has fixed advice (`BrokerRecoveryGuidance.AppendError`, `ForError`). It also follows the receipt returned by `send`, `send_message`, `send_with_attachments`, `reply_to_message`, `wait_for_receipt` or `get_message_receipt` while that receipt is `Accepted`, `Submitting`, `Submitted` or `Uncertain`, or `Refused` with reason `recipient_replaced` (`AppendReceipt`, `ForReceipt`).
- `agentbroker.pending_messages` (see Receiving during active work) comes last on a successful call that establishes an exact participant (`McpInboxHints.Append`). When a result carries both kinds, `agentbroker.recovery_guidance` comes first.

A client ignores any later block that is not a JSON object with a string `kind` in the `agentbroker.*` namespace, any `agentbroker.*` kind it does not know, and any member it does not know inside a kind it does. A later release may add a kind, or a member to an existing kind, without changing `content[0]`; it documents each new kind in this section. The repository's PowerShell client already works this way: it reads `structuredContent` or `content[0]` and treats later blocks as advisory (`tools/agentbroker/Invoke-AgentBrokerCollaborationMcp.ps1`). A `kind` member elsewhere is not an advisory, such as the attachments envelope inside message text (`agentbroker.attachments.v1`) or the envelope a native session receives (`agentbroker.peer_message`, `agentbroker.delivery_notice`).

The Worker check `ADVISORY_KINDS_EXACT_SET` collects the kinds in the tool results its own wire helpers parse, counts the later blocks it skips as plain text, and fails unless the kinds are exactly these two. It cannot see a kind on a path those helpers never receive (`tests/AgentBroker.Worker.Tests/AdvisoryKindChecks.cs`).

### Your own address

A Claude Code or Codex session the broker discovered natively has a directory row of its own (`claude:<session ID>` or `codex:<thread ID>`). When that row has `Receive` and `WakeIdle`, a message to it wakes the session when it is idle, so the session sends as that address and gives it to peers, without a duplicate mailbox or heartbeat. While the native session remains active, it can fetch pending messages explicitly with `read_inbox_page` using that same exact address. A row without them is observation-only (native delivery is off, or the client build is not reviewed and is not carried by its client's "Also wake updated ... builds" switch, which is on by default and needs the publisher's verified signature): replies to it are refused as `recipient_cannot_receive`, so such an agent registers a mailbox for replies. `whoami` returns the row either way, unchanged. The broker finds the process that owns the client end of the caller's loopback connection, walks up its parent processes, and returns the session a native adapter binds to the nearest `claude` or `codex` process. The match is by process ID and exact creation time, so a reused ID never matches (`tools/AgentBroker.Worker/CallerProcess.cs`, `BrokerRuntime.WhoAmI`). The walk stops at the nearest `claude` or `codex` process even when that process is no discovered session, so an agent started by another agent (`claude -p` inside a Claude session) is never told it is its parent. A Claude process hosts one session, so a Claude caller resolves whenever its session is discovered. A Codex caller never resolves to a row: it gets `no_native_session` (or `caller_elevated` when it runs elevated, as any caller does), because one Codex server process hosts every chat of its window, including chats discovery has not seen or whose observation aged out, so the server process never proves which chat is asking. An earlier draft named the one discovered chat on a server; Codex session 01a1855c's review showed that could return another chat's row. Without `whoami`, a Claude Code shell has its session ID in `CLAUDE_CODE_SESSION_ID`, and its row is the one whose `sessionId` is `claude:` followed by that value. A Codex shell has its thread ID in `CODEX_THREAD_ID` (a Codex VS Code chat, extension 26.1021.22027, reported it on 2026-10-29), and its row is `codex:` followed by that value. That is how a Codex agent finds its own row.

An elevated agent (a Claude Code or Codex session run as administrator) gets `caller_elevated`, not `caller_unresolved` or `no_native_session`. The broker runs at Medium integrity, and Windows refuses it part of the access to an elevated process, in one of two shapes. A same-user UAC elevation, as measured on one workstation, allows the limited query and refuses the full one (`PROCESS_QUERY_INFORMATION`), so the walk reaches the elevated claude process, which no adapter binds, and its refused full query answers (`QueryDenied`, asked of the nearest claude or codex process only). A process of another user, or a protected one, refuses even the limited query, so the broker finds the connection's owner but cannot walk it (`WindowsCallerProcessResolver.Compose`); that shape is handled by design and was not measured as a same-user elevation. Either way the broker cannot verify or wake the session. That is deliberate and not bridged: a broker able to drive an elevated session would let any Medium process drive one. Such an agent registers a mailbox with `register_agent`, or runs unelevated. Claude discovery skips the same session (its image cannot be read) and says so in Status as a count, `claude_session_elevated`, naming no process, session or path (`ClaudeNativeProvider.RefreshCoreAsync`): a note shown on its own line beside the healthy sessions' wake line, not an adapter error that would replace it. Until 1.7.0 it was skipped in silence. `caller_unresolved` still means no owner was found.

An agent with no native row registers a mailbox and sends its first message to the peer's native row, which wakes the peer, then waits with `wait_for_messages`.

Incarnations change. A Claude session gets a new one when its process restarts. A Codex chat's incarnation is the conversation on its running Codex server process (`codex-thread-v2`), so it changes when that process restarts, not when a view reconnects or another view takes ownership; each delivery still targets the owner rediscovered for that attempt. Until 1.4.0 it also covered the owning view, and on 2026-10-29 two new chats changed address within minutes of opening, which stranded queued messages and broke acknowledgements and replies to them. Upgrading to 1.4.0 changes every Codex address once. A send to an old incarnation is refused as `recipient_unavailable`. Read `list_sessions` again, or ask the peer to call `whoami`, and send again.

A Codex row also says which engine holds its thread, as a report only (owner's decision 2026-10-30): `engineBinding` on the `list_sessions` row, and on the sender's receipt what was observed at the message's latest attempt. The adapter asks Windows Restart Manager who has the thread's writer lock open (`%USERPROFILE%\.codex\thread-writer-locks\<threadId>.lock`), read-only, in the background after each discovery pass and within a budget (`tools/AgentBroker.CodexDesktopAdapter/CodexEngineBinding.cs`). A row the budget did not reach keeps its previous observation, whose `observedAt` says how old it is. A delivery's receipt carries the latest observation of its row, so no query sits between the owner re-check and the write. `bound` with `code_engine` or `desktop_engine` means exactly one holder, a codex.exe whose process ID and start time are a Code-owned engine's or the Codex desktop app's. Otherwise it is unbound with the reason: `lock_missing`, `lock_path_reparse` (a reparse point on the path, reported and never followed), `query_failed`, `no_holder`, `multiple_holders`, `foreign_holder` or `start_time_mismatch`. A codex.exe that cannot be read (it exited, or belongs to another user or an elevated VS Code) affects only a lock it holds, which reads `query_failed`. Nothing is refused, deferred or re-addressed on it, and a paired broker never receives it, neither on a row nor on a receipt. The Codex client's status in the AgentBroker pane counts bound and unbound rows by reason. Which webview of a window answered an owner lookup stays unverifiable, a limit of the vendor's router (`docs/DESIGN-REGISTER.md`, feature/broker-163).

This section and `whoami` exist because, on 2026-10-28, two agents on a second workstation registered mailboxes and one ran a 30-minute poller, although that one had a native row, and the owner carried one agent's address to the other by hand.

### Display hints

Display hints use the existing exact native address. `set_session_declaration` requires a current adapter-verified native row with Receive; `set_session_title` requires a canonical `claude:` row, so a `codex:` title is refused. Empty values clear a hint. `native_session_unverified`, `invalid_session_declaration`, `declaration_limit`, `invalid_session_title` and `session_title_limit` carry fixed recovery guidance pointing to `list_sessions`. Correct invalid values using the tool's bounds, or clear a hint you set when capacity is full; registering another session does not bypass those limits (`BrokerTools.Declarations.cs`, `BrokerTools.Titles.cs`, `BrokerRecoveryGuidance.cs`).

### Mailboxes and retention

A generic MCP registration has two lifetimes. Its presence lease lasts one minute, and every successful call that names the session renews it: reads, waits, sends, replies and acknowledgements. When presence lapses, the mailbox stays addressable for 24 hours after the owner's last call, provided the agent keeps the same `clientId` and incarnation. A retained mailbox still accepts sends and replies from local agents and paired brokers. Its owner can still read, acknowledge and reply, and the owner's next successful call restores presence. A new incarnation is a new mailbox. Measured, not inferred (Worker check `PRESENCE_CADENCE_180`): a mailbox whose owner calls once every 180 seconds is listed to paired brokers for exactly 60 of each 180 seconds, and still accepts their sends while it is not listed. To stay listed throughout, call at least every 50 seconds; back-to-back 25-second `wait_for_messages` calls do.

A present mailbox lists as `Idle` only while its owner is inside a wait (`wait_for_messages`, `wait_for_reply` or `wait_for_receipt`) and as `Unknown` otherwise, for local callers and paired brokers alike. Registering or renewing proves nobody reads the inbox; on 2026-10-28 a mailbox nobody had read for hours looked live to its senders. The store still records a present mailbox as `Idle`; only the directory view changes (`BrokerStore.PresentedDirectory`, which both `list_sessions` and `/federation/directory` serve). A local `list_sessions` lists a retained mailbox with `Activity` `Away` and its last, now past, `LeaseUntil`. Paired brokers, the peer directory and `/federation/directory` still list present sessions only, so `Away` never leaves this broker and no federation record changed. Native sessions keep the live-lease rule: once a native lease lapses, ordinary sends from or to it are refused. A registration cannot claim `Away` itself.

Retention is process-local and never persisted. A worker restart drops every registration while messages persist, and registering the same `clientId` and incarnation again finds them. At most 64 mailboxes are retained. A registration that would pass the 256-session bound takes the slot of the oldest retained mailbox with no outstanding message, then of the oldest retained one, and never a present session's. A local privacy or pause choice applies to a retained mailbox without restoring its presence.

For a native session, `session_unavailable` reports that the requested exact address is currently unavailable to the broker. The vendor chat may still be open. When the `agentbroker.recovery_guidance` advisory includes `guidance.availability.cause` set to `native_lease_elapsed`, the native discovery lease elapsed; this field does not identify why discovery stopped renewing it. Since 1.10.6 the report-only events file on this computer holds evidence of what discovery did with that row: `discovery_pass` lines say what each discovery pass did with the session's row, and a `session_forgotten` line names the exact address whose lease passed without renewal (see Acknowledged messages). Follow the guidance: refresh `list_sessions` and use the current complete address matching the intended broker ID and session ID, never a display label. If fresh matching native discovery is absent, wait for it; do not register the old native address. A generic mailbox instead re-registers its same `clientId` and incarnation.

### Long background work

Fetch `read_inbox_page` at milestones during long work. AgentBroker 1.10.5 includes the installed worker's `--watch-inbox` command. In Claude Code, run it through the background-command mechanism for your own native `claude:<canonical lowercase GUID>` address. Generic `mcp:` mailboxes, including ones registered by Claude Code, and Codex sessions use milestone inbox reads or incoming waits instead. The command polls the exact supplied address and exits 0 after a complete scan finds a pending, unexpired ID not listed in `--seen-ids`, after the supplied cursor or anywhere in the pending inbox when no cursor is supplied. When the background command reports completion, inspect its result and fetch the real messages; completion alone does not establish mail. The command prints fixed JSON metadata without message text and never sends, registers or acknowledges mail. A native notification can arrive for the same message, so handle each message ID once.

The caller first reads, retains and handles current mail, then supplies its exact Claude native address (`--broker-id`, the complete `--session-id` including its one `claude:` prefix, and `--incarnation`), the last cursor if available, and at most 64 handled IDs that may remain pending, as canonical lowercase GUIDs separated by commas with no spaces. Accepted, Submitting, Submitted and Uncertain entries are all actionable. Without `--cursor`, the first complete scan reports unseen pending IDs immediately and captures a watermark only when it finds none; with `--cursor`, that supplied cursor is the watermark. Every later scan starts from that same watermark without advancing it. A cursor reset (exit 24) requires a whole-inbox reread and the new cursor before rearming. Other confirmed `read_inbox_page` refusals end with exit 21: `invalid_inbox_cursor` needs a fresh cursor, and `session_unavailable` also needs refreshed discovery and verification of the current full address. The command never follows a replacement incarnation.

`--max-seconds` is required and accepts 1 through 31,536,000 seconds. There is no implicit duration or 48-hour ceiling. Parent monitoring uses both `--parent-pid` and `--parent-start`, where the latter is the process creation FILETIME from `StartTime.ToUniversalTime().ToFileTimeUtc()`, rather than DateTime ticks. Explicit `--unbound` replaces that pair and still requires the finite duration. `--interval-seconds` sets the pause after each scan: default 15, range 1 through 300 seconds, shortened to the remaining lifetime. Each authenticated `read_inbox_page` call is bounded by the smaller of 40 seconds and the remaining lifetime, or ends earlier when parent monitoring cancels it. Keep one fixed arm root and `--data` directory for the exact address (broker ID, session ID and incarnation). The arm root must exist, use a canonical drive-letter absolute path with no trailing separator, and contain no junction or symbolic link in its path. The data directory must also exist and use a canonical drive-letter absolute path with no trailing separator. A second process opening that same lock is refused with exit 25 while it is held; other arm roots do not coordinate. Invoke the worker by its explicit full path; for a default per-user install it is `%LOCALAPPDATA%\Programs\Desktop AI Companion\modules\agentbroker\worker\AgentBroker.Worker.exe`. The bare executable name in the worker's help is a usage synopsis.

Bind the parent pair to the actual Windows `claude.exe` ancestor, as shown in the offline guide. Git Bash's `$$` and `$PPID` are MSYS identifiers and must not be passed as Windows process IDs. A killed watcher, or an output failure, can leave no complete line; that never means the inbox is empty. Fetch the inbox before deciding whether to rearm.

The offline guide constructs required watcher arguments first, then adds the `--cursor` and `--seen-ids` pairs conditionally with `$watchArgs +=`. Keep their variables empty when those values are unavailable. The worker refuses an empty `--cursor` on any shell; Windows PowerShell 5.1 also drops an empty native argument, so the recipe never passes an empty optional value. Exit 20 means the finite lifetime ended or the watch was cancelled. Exit 23 means the bound parent ended or could no longer be confirmed as the same process; exit 2 handles a parent unconfirmed before arming. Exit 24 means the inbox epoch changed, after a worker restart or an in-process certificate-renewal reload: discard the cursor, reread the complete inbox and deduplicate IDs. Exit 25 means this arm root, data directory and full address's lock is held, possibly by another process. Exit 2 means arming failed before watching, including argument, parent or directory validation and pre-arm setup failures. Exit 26 can arise before or during watching, and output failure can hide mail already found. Neither a failed or incomplete result nor `unreported: 0` establishes an empty inbox; read the inbox before deciding whether to rearm. The offline guide's exit table gives the next steps.

### Waiting instead of polling

`wait_for_messages` returns at once when the session has incoming messages still `Accepted`, meaning not yet acknowledged. Otherwise it blocks until the store records a change or the deadline passes, then checks again. Acknowledge each message actually received, or the next wait returns it again. `wait_for_reply` waits the same way for replies to one message the caller sent; one message can receive several replies.

A recipient's acknowledgement never arrives in the sender's inbox, so a sender that wants to know whether its message was received uses `wait_for_receipt` (or polls `get_message_receipt`). It returns as soon as the receipt is `Delivered`, `Held`, `Refused`, `Expired` or `Uncertain`. `Submitted` only means a native adapter or a paired broker admitted the message for transport, so the wait continues until the recipient's own receipt, a refusal or the deadline. A receipt read after its message's deadline shows the deadline's outcome at once, by `get_message_receipt` and `wait_for_receipt` alike, rather than after the next delivery pass: `Accepted` and `Held` become `Expired`, `Submitted` becomes `Uncertain`, and `Delivered` and `Refused` stay as they are. A waiting `wait_for_receipt` also wakes at the message's deadline by itself, so it does not depend on another commit to notice the expiry. An `Accepted` message to a native session that has not been tried yet names its wait in the receipt's reason, read from the recipient's present state: `recipient_busy`, `recipient_awaiting_approval`, `recipient_interrupted`, `recipient_activity_unknown`, `recipient_wake_unavailable` (the row lists `Receive` without `WakeIdle`), or `recipient_unavailable` (its row lapsed or is gone); a message that was tried and deferred keeps that deferral's reason, such as `native_context_busy` (`BrokerStore.WithWaitReason`). A Codex row whose engine check could not complete lists `Receive` alone for up to five minutes, so messages to it wait instead of being refused and are delivered once a discovery pass completes the check; past that its queue is refused `recipient_cannot_receive` (`CodexNativeAdapter.DiscoverAsync`). On 2026-10-28 a sender asked to "poll for my acknowledgement" waited 25 seconds on its own inbox each time, while the acknowledgements came 3.5 and 8 minutes later and never appeared there.

The receipts a sender gets back (`send`, `send_message`, `reply_to_message`, `wait_for_receipt` and `get_message_receipt`) leave out the message text, which every poll used to hand back to the agent that wrote it, up to 16 KiB each time (`tools/AgentBroker.Worker/SenderReceipt.cs`). They keep the receipt's own nested shape (`message.id`, `message.sender`, `message.recipient`, `status`, `reason`, the times and `attempts`), so a client that read those reads them unchanged. `textBytes` is the text's length in UTF-8 bytes, or null once the broker no longer holds it (a tombstone); `get_message_receipt` with `includeText` true returns the text. The tools a reader uses (`wait_for_messages`, `read_inbox`, `wait_for_reply`) still carry it. Each receipt also tells its own age: `engineBinding` is the Codex engine report described above, as observed at the message's latest attempt. A paired broker's caller gets neither `busySince` nor `engineBinding`: both are this workstation's observations of its own processes. `readAt` is the broker's clock at the read, so `readAt` minus `updatedAt` is how long a `Submitted` or `Held` receipt has held its status, or how long ago an `Accepted` one was last tried. A deferred message's `busySince` starts at the first busy answer in its current run (`native_context_busy` or `native_recipient_busy`). An `Accepted` receipt waiting on `recipient_busy`, or a `Submitted` receipt, can instead carry the first fresh directory observation of its native recipient being Busy. These are observations of availability, not progress on the requested work. `busySince` and the delivery observations behind it live in the worker process only: `broker-state.json` keeps the schema an older worker reads, and a restart starts them again (`DeliveryObservations`). A native row that discovery can only call `Unknown` is listed `Busy` while its recipient was observed busy within the last 30 seconds. That is presentation in the local `list_sessions` only: the stored activity, which decides when a message is tried, is unchanged. A peer session reported a Codex recipient's receipt that sat `Accepted` / `native_context_busy` for about two hours while its row read `Unknown`, and two others sat `Submitted` with nothing telling their age.

Since 1.10.5, a local sender receipt can also carry `waits`: bounded observations of fixed reason codes, their directory or adapter source, first/last observation times and counts. The member is omitted when no observation exists and from paired-broker responses. It contains no peer message text. The history is process-local, tied to the exact admission and reset on worker restart; it is diagnostic history, not proof that the recipient read or executed a task (`BrokerStore.WaitingMail.cs`, `BrokerRuntime.View`, `SenderReceipt.From`).

Consecutive observations of the same directory reason are counted at most once per two monotonic seconds. An intervening reason or source change re-arms that directory count, so alternating directory and adapter observations can be counted more often. Adapter observations are counted as they occur; busy-state and capability changes still apply immediately.

Each reason's `FirstObservedAtUtc` and `LastObservedAtUtc` describe counted observations; a throttled repeat leaves those timestamps and its count unchanged. The separate monotonic freshness anchor refreshes on every observation, including throttled directory repeats.

A wait releases the store lock before awaiting a signal. Every committed change completes a signal, and a waiter captures that signal before it checks, so a message committed between the check and the wait still wakes it. Waits are local operations. Each session has at most one active wait per class (`wait_in_progress`): `wait_for_messages` and `wait_for_reply` share the incoming class, because both return the same `Accepted` reply and a second would only race the first for it, while `wait_for_receipt` returns no message and has its own receipt class, so it may run beside an incoming wait. The worker allows at most sixteen waits across every class (`wait_capacity`). A generic mailbox lists as `Idle` while any of its waits is active, until the last one ends. The 25-second bound stays inside the stdio bridge's 60-second request limit and ordinary client tool timeouts, so no client needs a longer timeout configured. A wait on a mailbox that nothing can reach is refused as `session_unavailable` instead of returning empty indefinitely. That covers a session never registered, one past its retention, and one lost to a restart. The refusal comes before anything is returned, even while messages are pending for that mailbox: `acknowledge_message` refuses them until the owner registers again, so a restart-lost mailbox's kept messages come back from the first wait after `register_agent` with the same `clientId` and incarnation. `wait_for_reply` applies the same rule to the original sender's mailbox.

Address removal completes the same change signal used for committed messages. A quiet native lease or generic mailbox's retention can end without a mutation, so waits also wake at that exact addressability deadline. They do not periodically reread retained message history. On worker shutdown, wait admission closes before HTTP draining and active waits receive `broker_stopping`. Reconnect after restart, refresh the exact session address and inspect existing receipts before retrying a message.

### Sending

`send` builds the message from the fields the caller supplies. A retry with the same `messageId` goes through the argument checks first, so a negative `ttlMinutes`, an empty `conversationId` or envelope-kind text (below) is refused before anything is compared. While the broker holds a record or tombstone under that ID, the retry is compared on the sender, recipient, text, the absence of a reply parent and, when given, `conversationId`, never on timestamps, and any difference is `message_id_collision`. A match must still pass admission's sender and ID checks (a sender on another broker than the caller's is `sender_mismatch`, for example); it then returns the stored receipt, marked `Expired` first if it is still `Accepted` or `Held` past its deadline, and ignores `ttlMinutes`. A record that keeps its text is compared by that text, and a tombstone (kept once a message sent from this broker is `Delivered` or `Refused`) by its SHA-256 (see Acknowledged messages). Once the broker holds neither, the retry is handled as a new message, except that it is refused `message_id_collision` while a terminal notice about that ID is still retained (see Delivery notices). `send` returns its receipt as the first content block, in the shape `send_message` returns. When the recipient is a local generic mailbox that nothing can wake (`Receive` without `WakeIdle`), a second text block says so: the mailbox sees the message only when its owner next waits or reads its inbox. A recipient on a paired broker gets no advisory, since this broker does not know its capabilities at send time (added in 1.4.1, `BrokerTools.SendTool`). `send_message` is for callers that need to supply the complete record; while the broker holds the original, a retry gets the stored receipt back only when it repeats the whole record, timestamps included. Since 1.10.5, `send`, `send_message` and `reply_to_message` refuse text that `AttachmentEnvelope.TryParse` reads as a JSON object whose `kind` is `agentbroker.attachments.v1`, a valid envelope or not (`attachment_envelope_reserved`); only `send_with_attachments` composes the envelope (`BrokerTools.Attachments.cs`).

### File attachments (opt-in, 1.10.5)

Off by default. The owner turns on **Allow file attachments with paired brokers** under Connections, then, for each paired broker that may send files here, ticks its Paired row in the Brokers card and presses **Allow or stop attachments** (while a pairing offer for the same broker ID and certificate is under Awaiting approval, the broker is listed only there, and the action needs a Paired row). The permission is pinned to the certificate hash recorded when that broker was paired, which stays fixed when it renews its certificate, and to that pairing, so pairing the same broker again starts denied; revoking sharing removes it first. If removing an allow cannot be saved to `attachment-peers.json` in the data folder, the broker is denied at once in memory, a revoke that made the removal stops with the broker still paired for the owner to retry, the worker retries the save at each attachment sweep (at most once a minute), and the pane says the change is not saved until a save holds or the worker restarts; a restart before the save holds brings the old list back. An allow that cannot be saved does not take effect and is not retried, and the button reports that the change failed (`AttachmentPolicy.cs`, `PeerFederation.RevokePeer`, `AttachmentStore.Sweep`, `AgentBrokerModule.Attachments.cs`). Allowed brokers stay allowed while the switch is off, and **Allow or stop attachments** can still stop one then; allowing a broker needs the switch on in the running broker (`LocalControlServer.cs`, `peer-attachments`), and the button also needs it on in settings (`AgentBrokerModule.Attachments.cs`).

`send_with_attachments` copies 1 to 4 regular local files (drive-letter paths, no reparse point anywhere in the path, no path inside the broker's own data folder except one shaped like a received file, `attachments\inbox\<broker GUID>\<message GUID>\<0-3>-<name>`, and the opened file's final path must equal the full form of the path given (`Path.GetFullPath`), compared without case, so a SUBST drive, a mapped network drive or a parent swapped to a junction before the open is refused), at most 8 MiB each and 16 MiB per message, into `attachments\outbox\<messageId>\`. A source that carries a Mark of the Web, and any file this broker received, is staged still marked (a zone stream that is empty, over 4 KiB or unreadable counts as internet), and `fetch_attachment` reports it as `internet` while that staged copy exists; once retention has removed the copy, `fetch_attachment` reports the entry, if at all, as `missing` with zone `local`. The SHA-256 is computed over the same bytes that are staged, so a later change to an original is never sent. The message text becomes a JSON envelope, `{"kind":"agentbroker.attachments.v1","text":...,"attachments":[{"index","name","bytes","sha256"}]}`, with names reduced to ASCII letters, digits, dot, dash and underscore. The 16 KiB text bound applies to the whole envelope, so the text's own budget is a little smaller (`attachment_text_too_long`). `BrokerMessage` is unchanged, so a 1.10.4 peer admits the envelope as ordinary text and fetches no file.

The recipient's broker pulls each file from the sender's broker over the same pinned mutual-TLS listener (`GET /federation/attachments/{messageId}/{index}`), before it admits the message. The sender serves a file only to the broker the message is addressed to, only while the message is Accepted or Submitting and unexpired, only while its staged copy still matches the message text and the declared size, and at most two at a time per paired broker; a staged file that exists but cannot be opened at that moment answers 503, as does a staged manifest that another program holds open without read sharing, and the recipient treats a 503 as transient, like a dropped connection. Before it pulls anything, the recipient runs some of the checks its store would make anyway (the sender's broker, direct addressing, expiry, and a recipient session that is available, not private and able to receive), so a message they refuse costs no file request; the store's other checks, such as a full recipient queue, come only at admission. It skips them while it holds a pull state or a deferral entry (the record of the first pull, below) for the message; both are kept in memory only, so the checks run again after a restart. While they are skipped the final admission decides, so a recipient lease that lapses during the re-forwards but is back at the final admission does not refuse the message. One message ID carries one text: another envelope or plain text under the same ID from the same broker is refused while the recipient holds a record under the ID (its store answers `message_id_collision`) or, failing that, a pull state for the ID or a received folder's `manifest.json` for it (`attachment_envelope_invalid`). The recipient requires `Content-Length` to equal the declared size before it reads a body byte, reads exactly that many bytes into memory, compares the SHA-256, and only then publishes the file to `attachments\inbox\<senderBroker>\<messageId>\` with a `Zone.Identifier` stream (ZoneId=3) written on the temporary before the rename (`LocalOutputFile.Save`, `PeerFederation.Attachments.cs`). Unverified bytes never reach the disk. Before a pulled message is admitted its files are checked again: that recheck, a last check of the allow and the admission run under one gate that the retention sweep also takes, so the sweep cannot remove the files in between. A refusal's deletion of the folder takes that gate too, and keeps the folder of a message that another forward of it has already admitted (`AttachmentStore.DeleteInbox`). The broker never runs or scans an attached file; it reads one only to hash it, to copy it into the outbox when it is sent (keeping any Mark of the Web, as above), to serve it to its recipient's broker, or to report it to `fetch_attachment`.

The forward waits at most 5 seconds for the pull. The sender forwards attachment messages on their own tasks, at most two at a time, so its delivery loop never waits on a pull (`BrokerRuntime.ForwardedInBackground`); a third attachment message is released with reason `attachment_forwards_busy` and tried again after the usual 5-second backoff. Any message to a recipient session waits while a forward to that session is in flight, and a later message from the same sender to the same session also waits while an earlier one is backing off (`BrokerStore.BeginDelivery`). When the pull takes more than 5 seconds, the recipient answers `attachment_fetch_pending` and lets the pull run on, until its bound below has passed; the sender then keeps the message Accepted with that reason and forwards it again after the usual 5-second backoff, unless the message's deadline has passed (it is Expired instead) or the sender's own bound below has. Until the recipient's bound below has passed, a new pull also waits, with the same reason, while the recipient already runs 4 pulls (2 for that sender broker), while that sender broker already holds 4 pull states or, for a message without a deferral entry, 16 deferral entries, or while admitted files leave room for the message but its bytes would take one of these past its limit: that sender broker's running pulls plus its finished, unadmitted folders (32 MiB), the same plus that broker's admitted files (128 MiB), or the whole quarantine, running pulls included (512 MiB). A message's own files kept from an earlier pull count once, inside its own bytes. The shares limit what one paired broker can add to the tables and to the unadmitted bytes, but the 4-pull limit and the 512 MiB are shared, so other brokers' pulls can still make a message wait. Because the sending broker hands one sender's messages to one recipient session over in the order it accepted them, a deferred message holds back the later ones, so deferral has two bounds. The recipient answers `attachment_fetch_failed` instead of deferring once 10 minutes have passed since the first actual pull it recorded for the message (its deferral entry); a wait for pull capacity records none, and the entry is kept in memory only, so a restart clears it, as does a cleanup after 70 minutes. The sender of a staged message keeps its own 10-minute bound from the first `attachment_fetch_pending` answer and refuses the message `attachment_fetch_failed` at the first such answer once it has passed; it stores that start beside the staged copy or, when it cannot, keeps it in memory until its worker restarts, and a stored start it cannot read back, or one later than its wall clock, can restart the bound. So a recipient restart cannot hold a staged message's pair for a day. The sender cannot tell a capacity wait from a running pull, so its bound counts every such answer; it is a head-of-line backstop, and the recipient's bound is the one a capacity wait cannot start (once started, it keeps running through capacity waits). The other outcomes are definite refusals: `attachments_refused_by_policy` (for example, attachments are off in the recipient's running broker, or it does not allow this sender), `attachment_envelope_invalid`, `attachment_mismatch` (the served `Content-Length` is missing or differs from the declared size, or the bytes' SHA-256 differs from the envelope's), `attachment_unavailable` (the sender's broker answered 404 for a file; causes include a staged copy that is missing, whose manifest is not the message text or whose length is not the declared size, attachments off at the sender, a message no longer Accepted or Submitting or past its deadline, and a 1.10.4 sender, which has no attachments route), `attachment_quarantine_full` (the recipient's admitted files leave no room: 512 MiB in all, at most 128 MiB from one sender broker; a folder whose message's record has just ended can still count as admitted until the next sweep) and `attachment_quarantine_unavailable` (the recipient's data folder is not usable for received files at all, for example a folder that is not plain local NTFS or one where it may not create the message's folder; a full disk or a refused file create is treated as transient instead, and a FAT32 volume may be too; after such a refusal the pane says so until a received file is next stored or the worker restarts, while attachments are on in settings and in the running broker and no allow-list change is waiting to be saved). A pairing revoked, or an allow withdrawn, during the pull takes effect at the next check that covers it, if the message gets that far: the allow is checked before each file is published and before admission, and the pairing after each answer's headers and after each body is verified, so a file or an admission already past its check can still go ahead. A forward still waiting when such a check ends the pull, or whose admission check sees the change, is answered `attachments_refused_by_policy`, and after a revoke any later forward is refused outright with a 403, which the sender records as `Uncertain`. These codes, like `attachment_fetch_pending` and `attachment_fetch_failed`, travel in the recipient's 409 answer (`PeerAdmissionRefusal`): a 1.10.5 sender that stays paired records `attachment_fetch_pending` as above and each other one as its own receipt's Refused reason, while a 1.10.4 sender knows none of them and records the message `Uncertain`. `PeerReceiptPolicy.KnownRefusalReason` is unchanged, because the recipient answers these codes instead of admitting the message, so no receipt it serves carries them. Once one forward of a message has admitted it, another forward of the same message that reaches the admission gate is answered with the admitted receipt while the two brokers stay paired, even if the allow was withdrawn in between, and the files stay. A forward that meets the withdrawn allow at its first check, before the other forward's admission, still answers `attachments_refused_by_policy` while the other admits; that refusal deletes nothing.

`fetch_attachment` gives the message's own sender or recipient session one file's name, size, SHA-256 and zone, and its local path only while the file is `ready`, which needs it still in place and matching its SHA-256; once retention removed a sent copy, an entry it still reports reads `missing` with zone `local`, whatever Mark of the Web the copy had. Each received folder also keeps a `manifest.json` naming its envelope, written before its first file and deleted with the folder's files; a publication into a folder and the broker's deletions of that folder never overlap (`AttachmentStore.FolderGate`), so no file is published into a folder while its manifest is being deleted. Sent copies and received files follow one rule, for local and paired messages alike: they leave when their message's record does, or 48 hours after their folder was created, whichever is first, and a sent copy also leaves once its message is Refused or Expired. A pull that was never admitted (a received folder counts as admitted only while a valid envelope from that same broker is admitted under its ID), and a staged copy with no record under its message ID, are deleted by the first sweep at which their folder is more than 15 minutes old and no pull for it is running, unless they went sooner; for example, an abandoned pull's folder goes at once (`PeerFederation.Abandon`), and so do the files a send just staged when the store refuses that send. Each file is deleted on its own: one that cannot be deleted at that moment, such as one another program holds open without delete sharing, stays until a later attempt can delete it, and does not stop the other files in its folder, the manifest included, from being deleted. The running worker's sweep, at most once a minute, applies these rules; while the worker is stopped nothing is deleted, and its sweeps catch up once it runs again. If the `attachments` folder itself is a junction or other reparse point, neither the sweep nor a refusal deletes anything in it until it is a plain folder again (`AttachmentStore.RootIsReparsePoint`). **Show attachments folder** reveals the folder's `README.txt`, which a broker started with attachments on writes; with the setting off, or before that file exists, it says what to do first instead.

### Reply budget

Every message carries `remainingReplies`. A `send` starts at 8, and a reply gets one fewer than the message it answers, so one chain of replies allows eight. `reply_to_message` on a message at 0 is refused as `reply_budget_exhausted`. To keep talking, `send` to the same peer with the same `conversationId`: the conversation keeps its ID and the new message starts at 8 again. The budget exists so two agents cannot answer each other automatically without end. It cannot be raised, because a paired broker refuses a message whose budget is above its own maximum of 8 (the `RemainingReplies` checks in `src/AgentBroker.Core/BrokerStore.cs`). The native envelope's preamble, the card and the `reply_to_message` description say this, because on 2026-10-28 agents on a second workstation started fresh conversations at the eighth reply.

`list_sessions` accepts optional `scope`, defaulting to `federated` for this workstation and explicitly paired brokers. Omitting `scope` or supplying JSON `null` uses that default. `scope: "local"` returns this workstation's existing view without fetching peers or waiting on their directory budget. Non-null values must be exact lowercase `local` or `federated`; other values return `invalid_scope`, with recovery guidance for local callers. A paired broker's caller gets this workstation's public present rows under either scope and receives no local recovery guidance. Scope does not change caller permissions, private-session visibility, or existing restrictions on metadata returned to peers. Use the same scope throughout one cursor traversal.

When presenting paired-directory rows, `list_sessions` compares their `LeaseUntil` against this PC's time shifted by that peer's latest clock sample, provided the sample is usable (`observed`) and within its five-minute freshness window. That sample can come from another authenticated response; an unusable latest sample falls back to this PC's clock. The offset affects only which peer rows are listed as live. It does not change stored message expiry, session leases, admission or authorization. See [paired-broker clock diagnostics](agentbroker-peer-diagnostics.md).

`list_sessions` and `read_inbox` return arrays in bounded pages. Both accept an optional `limit`, defaulting to 16; values outside 1 through 16 are refused. A full page may have more results: call again with the last returned key as the cursor. A shorter or empty page completes that scan.

| Tool | Cursor for the next page | Ordering |
|---|---|---|
| `read_inbox(session, limit, afterMessageId)` | Last receipt's `message.id` | Message GUID comparison |
| `list_sessions(limit, afterAddress, scope)` | Last session's complete `address` | Broker GUID, ordinal session ID, incarnation GUID |

Copy cursor values from the last result rather than constructing an offset or looking up the old record. An expired inbox record or disconnected session does not invalidate its key. These collections are mutable live views, not snapshots: new messages or sessions may appear before an existing cursor. Start each new poll without a cursor and finish its pages before polling again. Paging keeps large retained inbox histories within the stdio response limit without truncating message text.

### Acknowledged messages

Once a message sent from this broker is `Delivered` or `Refused`, whether by `acknowledge_message`, an eligible fresh local reply, a native adapter's receipt or a paired broker's, the broker drops its text and keeps a tombstone: the message ID, a SHA-256 of the text, the sender, recipient, reply parent, conversation, reply budget, status, reason and times (owner decision 2026-10-27). Since 1.10.5, a fresh reply settles its parent as `Delivered`/`reply_receipt` only when both endpoints are local, the recipient's current row has `Receive`, and the parent is unexpired `Accepted`, `Submitting`, `Submitted` or `Uncertain`. Parent settlement and reply admission share one commit; an existing stable-ID reply retry does not settle its parent. A reply never overwrites `Held` or a terminal receipt, and replying to a paired message does not acknowledge it. What needs no text keeps working. A `send`, `send_message` or reply retry with the same ID and text returns the original receipt, and different text is `message_id_collision`. `get_message_receipt`, `read_inbox` and `wait_for_reply` show the message with its status and an empty `text`; real message text is never empty, so an empty one always means the broker no longer has it. A late `reply_to_message`, and `wait_for_reply`, on an acknowledged original still route. Retain text before acknowledging or replying. If it must stay available, acknowledge `Held` before replying, then `Delivered` once it is no longer needed. Held does not extend the original deadline; mark `Delivered` before it expires.

Three kinds of message keep their text until their record goes. `Held` is not final: it can still become `Delivered`, `Refused` or `Expired`. `Expired` was never acknowledged, and its recipient can still read it. A message from a paired broker keeps its text because that broker settles its receipt by fetching it and comparing the whole message, text included, with its own copy. For the same reason `/federation/receipts/{id}` answers a tombstoned ID with 404, exactly as an unknown one, and never sends a receipt without its text.

Tombstones are kept in `broker-tombstones.jsonl` beside `broker-state.json`, one line each, and leave one day after their message expires, as a full receipt does. Only messages that still carry their text count toward the 4,096-message bound. Tombstones and those messages together are bounded at 65,536, so an acknowledgement always has room, and a send past that bound is refused as `message_limit` rather than dropping a tombstone. At the default 24-hour lifetime that sustains about 22 acknowledged messages a minute, where receipts with text sustained about 1.4. The measurements are in DESIGN-REGISTER under `feature/agentbroker-backlog-e`.

`broker-state.json` keeps the exact shape a 1.0.4 worker reads and holds only messages that still have their text, and 1.0.4 never opens the tombstone file. A rollback to a 1.0.4 worker therefore loads the data and loses only the tombstoned IDs: their receipts are unknown, a retry of one is admitted as a new message and delivered again, and a reply to one is refused. Starting this version again turns anything 1.0.4 acknowledged meanwhile into tombstones.

Since 1.10.6 the store directory (`<module data directory>\store`) also holds `broker-events.jsonl` and, after a rotation, `broker-events.1.jsonl`, beside `broker-state.json` and `broker-tombstones.jsonl`. It is a report-only record that the broker writes and never reads; nothing in it routes, retries, settles or admits a message. Each line is one JSON object. Its first key, `event`, names the event, and it ends with `eventAt`, the store clock's time of the write as an ISO 8601 round-trip string whose plus sign is written as a six-character JSON Unicode escape (compare parsed values, not text), followed by `eventsLost` only when earlier lines were lost or refused. No line holds message text, a label or title, an owner client ID, a process ID, a pipe name, a path or a diagnostic description. An `advisory_withheld` or `native_submission_stage` line is written only after the commit it describes has succeeded; `discovery_pass` and `session_forgotten` describe no commit. Four events are written:

- `advisory_withheld` (see the uncertainty advisory below): `messageId`, the exact `recipient` address, `uncertainAt` and `uncertainReason`, and the settlement's `settled`, `settledAt` and `settledReason`.
- `native_submission_stage`: one line for each settled attempt that a local `codex-native` or `claude-native` adapter took. An attempt whose settlement was rejected, for example because the recipient acknowledged the message during it, writes none, and so does a send to a paired broker, a generic mailbox or any other adapter. Its keys are `messageId`, the exact `recipient`, `receiptAttempts`, `lifetimeOrdinal`, `outcome`, `reason`, `stage` and `elapsedMs`. `receiptAttempts` is the claimed receipt's public `attempts`, which schema 1 keeps at 0 or 1, so it reads 1 for every attempt, a pre-frame deferral included. `lifetimeOrdinal` is this worker process's count of the message's settled native attempts in its current lifetime (the same recipient incarnation and admission): 1, 2, 3 with no gap, but only while its entry is retained. It restarts at 1 on a new admission or recipient incarnation, on a worker restart, and after its entry was evicted, since at most 4,096 messages are counted and the least recently counted goes first (`DeliveryObservations.CountAttempt`). `outcome` is the adapter's answer (`Submitted`, `Delivered`, `Held`, `Refused`, `Uncertain` or `DeferredNotSubmitted`), `reason` its exact reason code (at most 80 ASCII characters) or null, and `elapsedMs` the attempt's duration up to the adapter's answer on the runtime's monotonic clock, not counting the settlement commit.
- `discovery_pass`: written by each adapter's discovery loop on its first pass after the worker starts, then only when a pass differs from the last line that loop wrote; renewals alone write nothing. Its keys are `adapter`, `pass` (`completed` or `failed`), `failure` (the failure code, or null), `censusComplete`, `diagnostics` (the distinct diagnostic codes, never their descriptions), `changed` and `dropped`. `changed` lists, ordered by session ID, each row that is new or whose incarnation or outcome differs from the last completed pass the loop wrote, as `sessionId`, `incarnation` (the native incarnation the pass renewed or kept, or null) and `outcome`; `dropped` lists the session IDs that pass had and this one no longer reports. A failed pass writes its code with null `censusComplete`, `diagnostics`, `changed` and `dropped`, once while the same failure repeats, and the next completed pass is compared with the last completed one. Codex outcomes are `renewed`; `stale` (the desktop's last-seen time is at least 2 minutes old or more than 5 seconds ahead); `missing` (the owner lookup found no binding); `invalid` (the binding failed validation); `skipped_unreached` (the pass deadline came first, or a reconnect outlasted the pass); `skipped_slow` (the lookup ran out of time); and `skipped_failed` (the lookup failed). Claude outcomes are `renewed`, and `absent` for a session the previous completed pass returned and this one did not, once and with its previous incarnation; the line of the next completed pass lists it in `dropped` unless the session returned. An adapter that reports no per-row outcome has every row it returned recorded as `renewed`.
- `session_forgotten`: `adapter`, `address` (the exact `<broker ID>/<session ID>/<incarnation>`), `cause`, always `native_lease_elapsed`, and `leaseUntil`, the end of the lease's last registration. It is written once per lapse, when a native discovery lease this worker registered passed by the runtime clock without renewal: at the end of the first discovery pass after it, or within a pass that renews or replaces that session after its lease passed. A still-live incarnation replaced by a new one writes none, and neither does a generic mailbox or a paired broker's row. It does not say that the vendor chat closed, that the store has already removed the row, or why renewal stopped; the `discovery_pass` lines record what each pass did with the row.

`stage` is a cause family derived from the adapter, the outcome and the reason, while `reason` stays the exact cause; a family is classification, not proof of where delivery stopped (`BrokerRuntime.NativeStageFamily`). In precedence order: `submitted` and `delivered` come from the outcome. `owner_changed` covers `native_owner_changed`, `native_uncertain_owner_changed`, `native_uncertain_raised_owner_changed`, `native_uncertain_raised_server_incarnation_changed` and `native_uncertain_raised_stale_binding`. `pre_frame`, Codex only, covers `native_owner_rediscovery_unavailable`, `native_uncertain_rediscovery_timeout` and `native_owner_unavailable`, the reasons the Codex adapter gives when no model input was written. `answer_wait` covers `native_uncertain_timeout`, Codex `native_uncertain_native_error` and `native_submission_uncertain`, and `response_timeout_or_cancelled`, a library code that the Codex adapter maps to `native_uncertain_timeout` before the runtime sees it, listed for compatibility only. `connection` covers `native_uncertain_connection`, `native_receipt_capacity_reconnect`, `native_transport_unavailable`, and Claude `native_uncertain_raised_io` and `native_uncertain_raised_access`. Everything else is `other`, busy answers and refusals included. A Codex `native_uncertain_raised_<code>` reason that names no owner change is `other`, because the Codex adapter gives the same reasons for faults on either side of the turn frame.

This is new local persistence in 1.10.6. A Codex `discovery_pass` line holds the Codex conversation IDs the desktop lists, including conversations the broker never listed (`stale`, `missing`, `invalid`, or skipped with no kept binding), at most 256 changed rows plus at most 256 IDs an earlier pass listed and this one no longer does (dropped), written in full once per worker start and then only on change. They never leave this computer. Every other session ID and address in the file is one that receipts or `list_sessions` have held.

A line whose `event` is not 1 to 48 characters of `a-z`, `0-9` and `_` starting with a letter, or that is over 64 KiB once encoded, is refused; the largest line this release writes, a Codex `discovery_pass` with 256 changed rows and 256 dropped IDs, is about 48 KB. The file is bounded at 1 MiB and rotates once to `broker-events.1.jsonl`, replacing an older one. The bound is in bytes, so volume costs retention rather than space: a stage line is about 410 bytes, a message deferred every 5 seconds writes at most about 720 lines (about 295 KB) an hour, and a Codex chat answering `native_context_busy` for two hours writes about 600 KB, so on a workstation with busy chats older lines rotate out sooner. Writing it is best-effort. A failed write or a refused line never affects delivery, and it is counted into the next line written in the same worker process as `eventsLost`. A loss followed by no further write before the process exits is recorded nowhere, so the file can under-report but never over-report (`BrokerEventLog`, `BrokerStore.AppendEvent`, `BrokerRuntime.DiscoveryTrace.cs`, `BrokerRuntime.NativeStage.cs`).

### Delivery notices

A new local `Held` transition at or after the message deadline is refused as `message_expired`; an existing identical receipt remains idempotent. A late `Delivered` or `Refused` can still settle a Submitted or Uncertain record. Held does not extend its deadline, and paired receipts retain their existing reconciliation path (`BrokerStore.RecordReceipt`). A notice itself cannot be answered: `reply_to_message` refuses it as `notice_reply_refused` and points to `acknowledge_message`. Recipient acknowledgements, replacement refusals and peer-prefixed reasons keep their specific explanations. Otherwise-unclassified refusals for a remote recipient name its paired broker and ID (`BrokerStore.NoticeText`, `BrokerRecoveryGuidance.cs`).

Since 1.10.5, a local sender can receive a waiting advisory after its still-queued message has five minutes of fresh observed Busy time for its exact native recipient. The clock is a process-local monotonic lower bound, not the message's age, and resets on worker restart. Approval, interruption, unknown activity alone and unavailable metadata do not count as Busy. A gap of 30 seconds in the evidence ends the episode. Admission rechecks the message and recipient, admits at most 16 advisories per pass and uses a separate durable notice ID, so its retained record or tombstone prevents repeats without suppressing a later terminal notice. The advisory does not acknowledge, refuse or resend the original message. Inspect its current receipt; acknowledge the advisory itself as received. A sender on another broker gets no waiting advisory from this worker (`WaitingMailPolicy`, `AdmitDueWaitingMailNotices`, `WaitingNoticeId`, `BrokerRuntime.DeliveryLoopAsync`).

The pane's Waiting mail row covers registered local sessions, including mail that has been read but remains unacknowledged. It distinguishes pending, still-queued and busy counts and shows fresh observed Busy time as a lower bound, not execution progress or proof of a stuck task. Generic mailboxes have counts without native Busy timing. Once an eligible session's observed age reaches the worker's reported notice threshold, Status points to Waiting mail and the tray label reports mail waiting for a busy session; neither raises a question, speech or sound. The signals clear with unavailable or mismatched data, restart, disabling and shutdown; the tray reads its label when its menu opens. An older worker without the measurement reports measurement unavailable instead of zero waiting messages (`AgentBrokerModule.WaitingMail.cs`).

An I/O or access failure during waiting-advisory admission sets the `waiting_mail` status entry to `waiting_mail_notice_write_failed`. Further advisory attempts wait at least five seconds of monotonic time; the next successful pass clears that entry. Delivery loops continue to their normal claims, whose existing durable-store checks still apply (`BrokerRuntime.AdmitWaitingMailPass`).

Since 1.10.0, a local sender also receives an advisory when its message becomes `Uncertain`, including an interrupted submission recovered after restart. It names the original exact address, event time and reason. This is historical delivery information: the current receipt may already have changed. Inspect it with `get_message_receipt` and check with the recipient before choosing any new send. The broker never resends automatically, and Delivered still means receipt rather than work completion. An uncertainty advisory has an independent ID derived from the source lifetime; its retained record or tombstone prevents repeat advisories after restart or acknowledgement. An advisory not yet admitted is cancelled if the source resolves. An admitted advisory remains historical. Terminal notices retain their existing IDs. While an admitted terminal notice remains retained as a record or tombstone, its source UUID is reserved (`message_id_collision`), even after the source record prunes. Retained-source retries still recover their original receipt. Choose a fresh message ID for new work. No source retention is extended (`BrokerStore.WithSenderNotices`, `RebuildOwed`, `SenderNoticeId`, `NoticeText`, `Accept`).

Since 1.10.6, when the message became `Uncertain` for a reason a native adapter gave (one starting `native_`), its advisory first waits 120 seconds. The wait is measured on monotonic time from when the advisory became owed in the running worker, so a wall-clock step does not change it. A worker restart starts it again, so each restart can add at most one more wait. If the recipient settles the message within that time, no advisory is sent. The recipient settles it by acknowledging it `Delivered` or `Refused` (before or after its deadline, while the record is retained), by acknowledging it `Held` before its deadline, or with a fresh local reply before its deadline. A late reply, a retried reply or a reply from another identity does not settle it. A `Held` message is not final: it can still expire at its deadline, and its sender then gets the usual expiry notice. Whenever an unadmitted uncertainty advisory is cancelled because its message settled, whatever the cause and whether or not the sender was away, `broker-events.jsonl` records an `advisory_withheld` line. The line holds the message ID and exact recipient, the `Uncertain` time and reason, and the settlement's status, time and reason. Restart-interrupted submissions, deadline, paired-broker and other runtime causes (`submission_failed`, `submission_unconfirmed`, `adapter_result_invalid`) keep their immediate advisory, by choice. The receipt itself is unchanged: a sender reading it sees `Uncertain` at once and the recipient's own outcome afterwards (`BrokerStore.UncertainAdvisoryGrace`, `InGrace`, `Due`).

When a message sent from a session on this broker ends as `Expired` or `Refused`, the broker puts one notice in that sender's own queue. A native sender is woken with it like any other message; a generic mailbox's `wait_for_messages` and `read_inbox` return it. The notice comes from the reserved address `agentbroker:notices` on this broker. Its text names the message's ID and conversation, its recipient (with that session's label when the recipient is still registered as the notice is admitted; labels are not stored), when it was sent, and what happened. For an expiry it gives the delivery deadline and the number of delivery attempts, and says the deadline passed without a `Delivered` receipt: the broker cannot tell whether the recipient read the message, because a generic recipient can read one it never acknowledges. A native session receives the notice framed as an `agentbroker.delivery_notice` from the broker, not as an agent's request. Acknowledge it like any message. Nobody can reply to it, and a notice that itself expires produces no further notice.

This exists because, on 2026-10-28, two messages sent with a 20-minute lifetime to a generic mailbox whose owner never read it expired with zero delivery attempts, and their sender was never told. A native session is also delivered to only while it is idle, so a short lifetime can run out while its owner is busy.

A notice is owed to the sender's exact address (session ID and incarnation) until that address can take it: addressable, able to receive, with fewer than 64 messages outstanding, and within the store's message bounds. Since 1.10.6 a native-cause uncertainty advisory also waits until its 120-second wait has passed. Each delivery pass admits owed notices whose sender is back or has room. Passes come about every half second while the four delivery loops are idle, and later while all four are busy submitting to native sessions, which can take up to 20 seconds each. A notice always gets the maximum 24-hour lifetime, whatever the configured default, and it starts when the notice is admitted, not when it became owed. After a broker restart, the first delivery passes can commit expirations before discovery has re-registered the native sessions; those notices arrive once each session is rediscovered. What is owed is derived from the durable receipts, not kept only in memory: when the broker starts, every `Expired` or `Uncertain` record and `Refused` tombstone of a message a local session sent, whose notice exists neither as a record nor as a tombstone, is owed again, so a restart loses no notice. A notice is sent only while its source receipt is retained, which is until one day after the message's deadline. One that cannot be admitted by then is dropped, never sent late: that happens when the sender stays unavailable that long, or when the store, or the sender's queue, stays full that long. Room is counted as the commit will leave it, including the tombstones that commit writes, so a notice never pushes the store past a bound it could not reopen with. Messages the broker prunes during downtime of more than a day past their deadline produce no notice. On the first start after upgrading to 1.10.0, retained pre-upgrade `Uncertain` receipts from local senders can therefore produce historical advisories, as long as no notice with the derived ID is already retained. They remain subject to the same source-retention and admission bounds. A refusal's receipt is kept until one day after that message's deadline, so it can be almost two days old. The burst is bounded by those retained receipts and by the admission limits above. A message from a paired broker produces no notice here; its own broker settles it. For a message this broker sent to a paired broker, a verified `Expired` there is recorded as `Refused` with reason `peer_expired`, and the notice says it expired at the recipient's paired broker without a Delivered receipt; until 1.4.1 it was recorded as `recipient_receipt` and the notice said the recipient had refused it (`BrokerStore.RecordPeerReceipt`). No session can register as, send as, or send to `agentbroker:notices` (`reserved_session`). Terminal notice IDs are derived from the original message's ID as version-8 GUIDs that carry a fixed 32-bit marker. The broker refuses any newly submitted message whose ID carries that marker (`reserved_message_id`), so no new message can take a notice's ID and suppress it. Records stored by an earlier version are not checked: an earlier version accepted any caller-chosen ID, and a retry of such a message whose ID happens to carry the marker is refused too. Other version-8 IDs stay usable; the channel bridge derives its reply IDs that way. A notice's text is held to the configured message text bound, trimmed from the end if a small bound requires it. Notices are ordinary messages on disk, in the schema-1 shape, so a rollback loads them unchanged.

## Intended behavior

Each workstation runs its own local broker. Agents use MCP to discover reachable sessions, send a message, inspect a receipt, and reply. A compatible adapter wakes the exact existing idle session through its original client owner. Session names and working directories are display metadata, never addressing keys. Addresses include broker identity, vendor session ID, and an adapter incarnation.

The workstation endpoint may omit authentication when it is strictly bound to loopback. LAN communication uses authenticated HTTPS. A discovered broker initially exposes identity and connection information only. Explicit pairing authorizes current and future shared sessions in both brokers; private sessions remain excluded. Pairing never grants transitive trust or changes a session's tool permissions.

Discovery and transport stay local. This does not make Claude or Codex inference offline: the chosen agent's existing model provider still applies.

## Agent conversations

Two agents (Claude Code, Codex or any MCP client) keep a conversation across their turn boundaries without a sidecar process:

1. Each agent calls `whoami` (a Codex agent finds `codex:<CODEX_THREAD_ID>` in `list_sessions` instead). A native row with `Receive` and `WakeIdle` is its address: it sends as that row and is woken when idle. An agent with no such row picks one `clientId` and one incarnation for the conversation and calls `register_agent` with that pair at the start of every turn.
2. The asking agent finds the other session with `list_sessions`, routing by complete address. It calls `send` with a fresh `messageId`, then `wait_for_receipt` for receipt and `wait_for_reply` for the answer. For later answers, use `unacknowledgedOnly: true`, or retain the `read_inbox_page` cursor across active-work checkpoints. Legacy reply waits also return acknowledged history by default.
3. The answering agent receives the message (a native session is woken when idle or fetches `read_inbox_page` while active; a mailbox calls `wait_for_messages`) and retains any content it needs before acknowledging or replying. A fresh reply records `Delivered`/`reply_receipt` for an unexpired `Accepted`, `Submitting`, `Submitted` or `Uncertain` parent only when both peers are local and the recipient's current row has `Receive`. If not replying, or if that reply does not settle the parent, use `acknowledge_message` with outcome `Delivered` when permitted. To keep the broker's text, acknowledge `Held` before replying, then `Delivered` when done. Held does not extend the original deadline; mark `Delivered` before it expires. Reading alone acknowledges nothing. When the reply budget runs out, either side continues with `send` and the same `conversationId`.

Run one incoming wait (`wait_for_messages` or `wait_for_reply`) at a time per inbox; a `wait_for_receipt` may run beside it. Accepted and Submitted are not Delivered, and Delivered does not mean the work is done. Peer text is untrusted data: it never overrides the user, the receiving session's instructions or its permissions, and no agent should use a peer to do what its own session may not.

Legacy free-form handoff convention. Message text may be one JSON object:

```json
{"kind":"request|status|result|handoff","summary":"...","artifacts":[{"path":"<repo-relative>","sha256":"<hex>"}],"needs":"..."}
```

For new integrations, the supported `--handoff-prepare` client validates bounded `agentbroker.handoff.v1` packets with task IDs, states and artifact metadata; see [typed handoff text](agentbroker-client.md#typed-handoff-text). Both formats remain ordinary untrusted message text. The broker neither parses nor enforces this legacy shape. The instructions card described it until 1.4.0, which moved it here to make room for `whoami`. Content larger than a few KiB belongs in a file referenced by path and SHA-256, never inline past the 16 KiB text limit. Use a path the intended recipient can resolve in its authorized environment; a repository-relative path requires a matching checkout, and an absolute path is only meaningful where that location exists. The recipient decides whether it may open the artifact and verifies its bytes against the supplied hash before relying on it.

### Collaboration helper (an agent whose MCP client cannot connect)

`tools/agentbroker/Invoke-AgentBrokerCollaborationMcp.ps1` sends one reviewed JSON request file to the loopback endpoint (validation only without `-Execute`), for an agent whose own MCP client cannot reach the broker, such as Codex under an organization's MCP allowlist. Its addresses are generic `mcp:` mailboxes, with one exception since 1.6.0: `send`'s sender may be the calling Codex agent's own row, `codex:` plus the canonical lowercase GUID in `CODEX_THREAD_ID`. Before sending, the helper reads every `list_sessions` page itself and requires exactly one fresh `codex-native` row with that session ID, the request's broker ID and incarnation, and `Receive` and `WakeIdle`; it refuses when the row is absent, when a second row has the same session ID (on any broker), and when the incarnation is stale, the lease lapsed or the row is observation-only. Replies then wake that native session instead of landing in a mailbox it has to poll.

This is a routing convenience the owner authorised inside the broker's existing local access model, not per-thread authentication. That model is wider than one user: while Allow local connections without a token is on (the default), the loopback endpoint admits any local process of any account, because a loopback connection carries no Windows identity (`WorkerApplication.cs`); turning it off, so callers need the bearer token from the user-scoped control pipe, is what makes it same-user. No trusted per-thread operating-system marker exists, and `CODEX_THREAD_ID` (like `CODEX_SESSION_ID`) is whatever the process running the helper says it is. Everything else is unchanged: recipients stay generic-only, `send_message` stays generic-only, `read_inbox`, `wait_for_messages` and `acknowledge_message` on a native row stay refused, live `reply_to_message` stays refused, and a `claude:` address is never admitted. `wait_for_reply` and `wait_for_receipt` name only a message, and the broker waits as that message's sender, so the helper first reads the original with `get_message_receipt` and refuses the wait unless its sender is a generic mailbox. The request file's bytes reach the broker unchanged, so a retry keeps its `messageId` and sender.

## Claude channel bridge (opt-in)

Claude Code's [channels](https://code.claude.com/docs/en/channels-reference) research preview lets an MCP server push messages into an open interactive session. `AgentBroker.Worker.exe --mcp-channel --data <broker data directory> [--label <text>] [--private]` is such a server, and it is opt-in only: nothing configures it, and the **Connect Claude MCP** button is unchanged.

The bridge registers one generic inbox for its whole lifetime, with one `clientId` and incarnation and the given label (`Claude Code channel` by default), and registers again between waits once 20 seconds have passed, so a worker restart cannot strand it. It waits on the inbox and pushes each new message once as `notifications/claude/channel`. The message text is the tag body. `message_id`, `conversation_id`, `sender_broker`, `sender_session`, `sender_scope` (`local` or `paired`), `expires_at` and, for a reply, `in_reply_to` become tag attributes. Its two tools act on that inbox only:

| Tool | Parameters | Effect |
|---|---|---|
| `acknowledge` | `message_id`, `outcome` (`Delivered` by default, `Held` or `Refused`) | Records the explicit recipient receipt through `acknowledge_message` when permitted; use `Held` before replying to keep text, then `Delivered` before its original deadline |
| `reply` | `message_id`, `text`, optional `reply_id` | Answers through `reply_to_message` and settles an eligible fresh local parent as described below; without `reply_id` the ID is derived from the message and text, so an identical retry returns the same reply receipt without settling its parent |

A push or read is not an acknowledgement. Claude Code does not acknowledge a notification, and it drops one silently when the session did not opt the server in, so a push alone leaves its receipt `Accepted`. A fresh channel `reply` records `Delivered` with reason `reply_receipt` and removes the parent's text atomically with the reply only when both peers are local, the recipient's current row has `Receive`, and the parent is unexpired `Accepted`, `Submitting`, `Submitted` or `Uncertain`. Retain content first. To keep the text, `acknowledge` it as `Held` before replying, then `Delivered` when done. Held does not extend the original deadline; mark `Delivered` before it expires. A reply leaves `Held` unchanged. Otherwise acknowledge `Delivered` explicitly when permitted, or `Refused` when permitted to decline. Pushes come from the oldest 16 unacknowledged messages, ordered by their creation time, so newer ones wait in the broker until older ones are acknowledged. Before each push the bridge re-reads the owner's choices over the management pipe. A muted inbox is pushed nothing, and its messages wait. A message from a broker that is no longer paired, or from a paired broker to a private inbox, is refused. The bridge never declares `claude/channel/permission`, so no agent that can message the inbox can answer the session's tool-approval prompts. It answers MCP revision 2026-07-28 with 2025-11-25, because Claude Code does not register a channel on the newer revision. Its broker calls appear under Other clients in **MCP client traffic**.

To try it, the person who will watch the session adds the server and starts an interactive CLI session with the development-channel flag:

```powershell
claude mcp add --transport stdio --scope user agentbroker-channel -- "<module folder>\worker\AgentBroker.Worker.exe" --mcp-channel --data "<AgentBroker data directory>"
claude --dangerously-load-development-channels server:agentbroker-channel
```

Accept the development-channel warning, then check that the startup notice names `server:agentbroker-channel`. Channels need claude.ai or Console authentication, and Team and Enterprise organizations must enable them (`channelsEnabled`). Claude Code ignores the development flag with `-p` and through the Agent SDK. The Claude VS Code extension passes `--channels` only, so until this server is on an approved channel allowlist it is a CLI route; see the [compatibility evidence](agentbroker-client-compatibility.md#claude-channels-2026-10-27).

## Delivery contract

A native session receives each peer message as a short preamble plus one JSON object of kind `agentbroker.peer_message` (a delivery notice keeps its own `agentbroker.delivery_notice` envelope): the message and conversation IDs, the reply parent, the exact sender and recipient addresses, `senderLabel`, `senderScope`, when it was sent (`createdAt`), the deadline, the remaining reply budget and the quoted text. `senderLabel` is the label a local sending session registered with, looked up on its exact address when the message is delivered, or `null` once that address is gone. A sender on a paired broker always has a `null` label, because the broker does not fetch the remote directory to deliver. The label is self-declared and identifies or authorizes nothing, and the preamble says so. `senderScope` is `local` for a session on this broker. For one on a paired broker it is `paired broker "<name>" <broker ID>`, where the name is the one that broker advertised when the pairing was approved (its `--name`, by default its machine name). The name is for display only; the broker ID is the one in the sender address. Routing and trust stay with the exact sender address. A native adapter refuses a message whose whole envelope, these fields included, exceeds its limit (32 KiB for Codex); a long label adds up to about 1 KB. These fields were added on 2026-10-28, after a recipient could tell who was asking only by remembering a GUID. `createdAt`, and the preamble's sentences on it (the sender's own timestamp, while delivery follows the order this broker accepted the messages) and on continuing at `remainingReplies` 0, were added on 2026-10-29, after agents on a second workstation reported messages arriving out of order.

One sender's messages to one recipient are delivered in the order the broker accepted them: a newer message waits while an older one for the same pair is still pending but cannot go yet, for example during the 5-second backoff after a deferral, and that older message's expiry ends the wait. Other senders to the same recipient are not held. A Codex chat whose owning view is missing when the broker rediscovers it, before any turn request is written (discovery itself sends only control frames, never model input), defers as `native_owner_unavailable` and is retried, where it used to be refused. Since 1.10.6 the second owner lookup, the one inside the submission after the first lookup succeeded, also defers when it runs out of its own time, is cut by the 20-second attempt deadline, or fails on I/O, and so does an attempt whose deadline expires while waiting for the connection or just after that lookup. All of these come before any turn request is written, and defer as `native_owner_rediscovery_unavailable`, which the sender's receipt shows in its waits with a count. A failure of the first lookup still defers as `native_owner_unavailable` and does not count. After three `native_owner_rediscovery_unavailable` deferrals in a row, the fourth consecutive one for that message settles it `Uncertain` as `native_uncertain_rediscovery_timeout`, `native_uncertain_raised_cancelled` or `native_uncertain_raised_io`, because a lookup that fails on every attempt would otherwise hold that sender's later messages to the recipient until the message expires. The count belongs to one message lifetime to one exact recipient. An answer that reached the owner or settled the attempt restarts it: a turn accepted or rejected, an uncertain submission, the owner's busy reply, or an owner missing at that lookup. A deferral that never reached the library does not count and does not restart it, for example `native_not_submitted` when the deadline ran out during the fresh client check. The count is forgotten after ten minutes without an update, or when the worker restarts. An uncertain Codex submission records the library's cause in its reason: `native_uncertain_timeout`, `native_uncertain_native_error`, `native_uncertain_owner_changed` or `native_uncertain_connection`, and `native_submission_uncertain` when none is known. An exception out of a native submission records its cause too: `native_uncertain_raised_io` or `native_uncertain_raised_cancelled` for either client, `native_uncertain_raised_<code>` for a Codex library code, and `native_uncertain_raised_access` or `native_uncertain_raised_timeout` for Claude. Any other exception out of a submission, local or forwarded to a paired broker, settles that message `Uncertain` as `submission_failed`, and the next message to that recipient goes as usual. If a delivery or receipt loop itself fails unexpectedly, Status names it (`delivery: loop_failed` or `receipts: loop_failed`, with a count and the time of the last failure) until the worker restarts, and the loop runs again after a pause that starts at one second, doubles after each failure up to a minute, and starts again from one second once the loop has run a minute without failing.

Accepted, submitted, delivered, held, refused, expired, and uncertain are different outcomes. The store persists admission before a delivery attempt. Repeated message IDs with an identical payload recover the existing receipt, after acknowledgement included; conflicting reuse is rejected. `send` compares only caller-supplied fields, so a retry recovers its receipt even when the client regenerated its timestamps. A lapsed generic presence leaves its mailbox reachable (see Mailboxes and retention); a lapsed native session does not. Reply creation is atomic, so concurrent retries preserve the first reply's timestamps and receipt. Expiry bounds a message's delivery window; a retained message can receive a later reply with its own deadline and remaining reply budget. A broker restart invalidates session registrations. An interrupted native submission becomes uncertain rather than blindly replaying a prompt that might already have started a turn.

Queues, session leases, message size, retention, paired brokers, and reply depth are bounded. `tests/Measure-AgentBrokerCoordination.ps1` measures what those bounds cost, one fresh process per sample, interleaved across configurations. Busy, approval-blocked, interrupted, disconnected, and idle states remain distinct. A label match or persisted transcript never proves a session is live or wakeable.

## Identity, privacy, and operating limits

The local HTTP listener binds the literal IPv4 loopback address. It answers two Host authorities, both naming its own port: `127.0.0.1:<port>` and `localhost:<port>`, the second because a managed Claude Code allowlist can admit local MCP servers only as `http://localhost*` URLs. Any other host name, and either name with another port, gets 403. No IPv6 listener is bound: Claude Code 2.1.293 given the localhost URL connected through the IPv4 listener on a workstation that resolves localhost to `::1` first. Optional token authentication is independent of LAN authentication; browser origins and DNS aliases do not inherit local authority. The management interface uses an explicitly user-owned, protected named pipe. Its DACL denies network logons, and clients verify the connected server process and pipe ownership before sending a request. It is never exposed on the LAN listener.

Windows Schannel requires a named private key for TLS. AgentBroker creates a current-user Microsoft Software KSP key with a nonexportable policy. Its encrypted `tls-identity.dat` stores public certificate metadata and the exact owned key name. No raw private-key file, certificate-store installation, administrator action, or OS trust change is required. Identity survives same-user, same-path restarts. Moving the data directory or losing the Windows key fails closed; copying data to another machine is not an identity backup. A new identity requires explicit pairing again.

AgentBroker 1.9.0 renews its five-year TLS certificate at startup when 90 days or less remain. A running worker checks hourly and drains before recreating itself for renewal. The original paired certificate hash stays fixed, and renewed certificates carry a bounded proof tied to its original public key. An upgraded peer can authenticate after missing several renewals. The live certificate must remain valid on the local clock. Owner stop, parent exit, durable failure and cleanup failure prevent renewal from overriding shutdown. The [certificate design and validation record](audits/agentbroker-certificate-continuity-20261107.md) describes the checks.

If renewal metadata replacement fails after `tls-identity.dat` disappears, the worker preserves any remaining sealed `identity-<guid>.tmp` in the same data directory. Startup fails closed and does not promote that file automatically. Preserve it and the existing Windows key for explicit identity recovery.

Upgrade paired brokers to 1.9.0 or later before renewal becomes due. Older workers reject renewed TLS certificates. After the first renewal, the identity metadata uses version 2, which older workers cannot load. Renewal keeps the existing private key; replacing a lost or compromised key still needs explicit identity recovery and pairing.

Pairing shares current and future discoverable sessions directly between the two approved broker identities. Each session can be made private or muted. These choices persist across discovery and restart. A muted session cannot receive automatic peer input. Native client approvals remain authoritative; messages cannot approve tools or elevate either agent's permissions.

File attachments (1.10.5) are off unless the owner turns them on, and a paired broker can send files only after the owner allows that broker; an allow persists while the switch is off, and stopping one with **Allow or stop attachments** needs this broker running but not the switch. A running broker keeps the switch value it started with until it restarts. Received files are untrusted peer data in a quarantine folder under the module's data folder, marked as downloaded from the internet; no approval or permission travels with them. They use the same LAN listener and firewall rule as messages; nothing new is opened.

The current durable store is intended for low-volume workstation coordination. Defaults bound messages that still carry their text to 4,096, those together with acknowledged-message tombstones to 65,536, raw text to 16 KiB per message, registrations (present or retained) to 256 with at most 64 retained mailboxes, mailbox retention to 24 hours after the owner's last call, paired brokers to 32, pending messages per recipient to 64, a conversation to eight replies, and a blocking wait to 25 seconds with one incoming wait and one receipt wait per exact session and sixteen waits total per worker. Native adapters may impose a smaller envelope limit and explicitly refuse oversized input. Receipts and tombstones remain until message expiry plus one day; reaching capacity refuses new messages rather than silently dropping existing receipts. Each state transition replaces a flushed snapshot, and a message this broker sent that becomes `Delivered` or `Refused` also appends one tombstone line, so the snapshot holds only messages that still have text. The measured costs, before and after tombstones, are recorded in DESIGN-REGISTER (O-agentbroker-02 and `feature/agentbroker-backlog-e`). Idle directory polling does not rewrite durable state.

## Decisions

| Decision | Reason |
| --- | --- |
| Deliver AgentBroker and directly relevant regressions in this effort | The user accepted narrowing the earlier request to clear all 73 unrelated backlog items. |
| Allow one-time setup/restart for explicitly enabled, version-checked adapters | Required for normally opened desktop and VS Code sessions without a stable external submission API. |
| Prefer an existing desktop-owned IPC route over a Codex executable override on Windows | The installed desktop's override changes sandbox/bootstrap initialization. |
| Preserve Claude peer classification | Its exported child token is treated as self-sent and can bypass default inbound mode parity. |
| Do not read native Claude peer key records during source investigation | Live credential access requires a separate exact platform approval under sensitive-file policy H05, and W06 if stored in a workspace. |
| Use a separate self-contained worker for the HTTP server | Keeps the host's runtime requirements and plugin ABI stable. |
| Pair broker identities, including future shared sessions | Matches the requested broker-level authorization. |
| Require both brokers to approve the complete 128-bit comparison code | A discovered name, pairing request or single approval cannot authorize a spoofed peer. |
| Keep native delivery off until explicitly enabled | Version pins and live acceptance are separate from successful generic MCP transport. |
| Treat expiry as a per-message delivery deadline | Long-running tasks can send a fresh reply after the original message's delivery window. |
| Revalidate a paired identity before saving a discovered address change | Restarts and DHCP changes recover without trusting an unverified discovery announcement. |
| Retain unrelated and externally blocked backlog entries | Closing them without implementation or evidence would hide remaining work. |
| Keep a generic MCP mailbox addressable for 24 hours after its owner's last call | Turn-based agents fell off the bus between turns, and a renewal sidecar process was the workaround. Retention is process-local and peers still see presence only, so no federation record or persisted state changed. |
| Never retain a native session | Ordinary sends require its current native discovery lease; a lapse makes that exact address unavailable to the broker even when the vendor chat remains open. |
| Bound blocking waits at 25 seconds, one per class and sixteen total per worker | Stays inside the stdio bridge's 60-second request limit and ordinary client tool timeouts without configuration; each wait occupies a request. |
| Refuse a wait on an unreachable mailbox | An empty result would look like silence forever after a restart; `session_unavailable` tells the agent to register again. |
| Add `send` beside `send_message` | Clients regenerate timestamps on retry; comparing only caller-supplied fields keeps an honest retry from colliding, while `send_message` keeps its exact-record semantics. |
| Publish the protocol as MCP server instructions | Every client receives the same short card in `initialize`, Codex included through the stdio bridge, instead of a per-client setup note. |
| Offer the Claude channel bridge as a separate, hand-configured server | Custom channels are a research preview that needs an interactive per-session development flag and, in Team and Enterprise organizations, an organization switch; wiring it into **Connect Claude MCP** would present it as a supported route. |
| A channel push alone leaves its receipt Accepted | Claude Code never acknowledges a notification and drops it silently when the channel is not registered. The session may acknowledge explicitly when permitted or make an eligible fresh local reply; reading or pushing alone records no receipt. |
| Keep a tombstone, not the text, of an acknowledged message this broker sent | Owner decision 2026-10-27: receipts with their text filled the 4,096-message bound at about 1.4 messages a minute. Retries, receipts and replies need only the record, and a separate tombstone file leaves the state a 1.0.4 worker reads unchanged. A paired broker's messages keep their text, because its receipt check compares the whole message. |
