# AgentBroker implementation and validation

AgentBroker adds local MCP messaging and paired LAN brokers through a separate, self-contained worker. Native GUI delivery is explicitly enabled and subject to client compatibility and publisher-trust checks. The evidence below distinguishes automated checks from live GUI acceptance.

The [campaign validation and disposition record](agentbroker-180-validation.md) tracks the initial 1.8.0 publication, the subsequent 1.9.0 repairs, their tests and explicit acceptance limits.

## Setup

Install AgentBroker from the module catalog, then enable it in its options pane. Its workstation MCP endpoint is `http://127.0.0.1:7432/mcp`; the same listener answers `http://localhost:7432/mcp`. LAN HTTPS uses port 7433 by default. The worker includes its runtime, so normal operation does not require an ASP.NET installation or administrator privileges. The optional Windows Firewall setup action requires administrator approval.

Use **Connect Codex MCP** or **Connect Claude MCP** in the module options to add the named, user-scoped `desktop-ai-companion-agentbroker` entry through the vendor CLI. Existing entries are never silently replaced. Claude Code prefers the broker's live loopback HTTP endpoint when the user-only management connection confirms that no token is required. Newly added Codex entries and confirmed token-required connections use the stdio bridge, which retrieves its current connection through that pipe. An existing Codex HTTP entry for this broker's exact loopback endpoint is recognized and retained. A failed Claude connection-info request asks the person to refresh status before setup. Neither route persists a broker access token in client configuration. The buttons find each CLI the way the companion's model calls do: on PATH, where an npm shim counts as the binary it starts and that binary is run directly, never the shim or cmd.exe; then the PATH saved for new terminals, npm's default prefix, Claude Code's own installer, WinGet's package folders, and last the copy inside VS Code's Claude Code extension. The located binary starts once. A failing CLI is never followed by another candidate, and PATH is never changed.

**Connect Claude MCP** configures Claude Code, including its VS Code extension. After successful registration, start a new Claude conversation and check `/mcp`; reloading VS Code is not normally necessary. Managed policy can allow HTTP URLs separately from stdio commands, and a loopback URL still needs approval when an allowlist is enforced. When the allowlist refuses the `http://127.0.0.1:<port>/mcp` URL (`not allowed by enterprise policy`), the button adds `http://localhost:<port>/mcp` once more, the same listener under the name a policy can admit as `serverUrl` `http://localhost*`. If registration is still refused, ask the policy owner to approve one of those exact local server URLs or the stdio command and arguments, as applicable, or deploy the approved server through managed configuration. An explicit deny and every other failure are final: AgentBroker does not retry another transport or override policy after a refusal. See [Claude's managed MCP documentation](https://code.claude.com/docs/en/managed-mcp).

An organization can delegate a soft allowlist that people may extend in their own settings. In that case, the reviewed `tools/agentbroker/Grant-ClaudeLocalMcpAllowance.ps1` helper can append only the exact local AgentBroker URL after an explicit approved action. It retains a private rollback copy and does not change managed files, policy locks, denials or server definitions. Managed restrictions still apply, and the normal vendor CLI remains the final authority. A locked allowlist or other refusal requires the policy owner's action.

Registration confirms that the server definition was saved. Connection additionally requires an MCP handshake and a usable tool list. The reviewed `Connect-ClaudeMcpEntry.mjs --verify-http` mode checks only the fixed AgentBroker name and exact local HTTP entry, then reports fixed status fields without forwarding CLI diagnostics, headers or configuration. It runs no model or native wake command. A successful CLI check proves that CLI connection; a normally opened VS Code conversation must still load the entry and show it connected in `/mcp`.

Metadata discovery defaults on. Native Codex peer delivery and Claude peer credential access default off. Enable a native adapter only after reviewing its [compatibility requirements](agentbroker-client-compatibility.md). Claude uses its peer-class token locally and delegates inbound acceptance, holding and refusal to the recipient's own policy. It never forwards that credential to another agent or workstation.

The **Wake existing Codex sessions** and **Wake existing Claude sessions** switches enable automatic delivery into normally opened idle client sessions. They are needed for that behavior. MCP discovery, inbox polling and replies work without native wake, so the switches are separate opt-ins. Beneath each, **Also wake updated Codex builds** and **Also wake updated Claude builds** (both on by default; Claude's since the owner's decision of 2026-11-02) let a client build that is not exactly pinned be woken when Windows verifies its publisher's signature, so a client's own update does not stop wake-ups until a re-pin ships; off keeps exact pins only (`docs/agentbroker-client-compatibility.md`, "Update-tolerant native delivery contract"). Host 1.6.1 and module 1.0.2 refresh status in place without resetting pending edits; a worker that misses its startup deadline reports an unavailable state rather than remaining indefinitely at Starting.

### MCP connection status

Module 1.0.3 added MCP endpoint readiness and Claude/Codex last-seen activity. **Status** now carries the readiness summary, such as `MCP ready.`, while **MCP client traffic** carries details such as `Claude client: seen just now` and `Codex client: not seen`. Only successful MCP traffic counts. Saved client configuration and discovered native sessions do not establish an MCP connection.

HTTP clients connect on demand, so an idle client does not become disconnected after an arbitrary timeout. Last seen means successful traffic observed since this worker started; observations reset on worker restart. A client can still display a cached connection before it sends its next request. Older stateless tool requests omit client identity and appear under Other clients; initialization or supported per-request identity supplies the Claude/Codex label. Labels are self-reported display information and grant no access.

These observations retain only three fixed client categories and timestamps, plus the address of each generic inbox whose own `register_agent` request identified its client. Status uses the existing refresh cycle, without launching vendor commands, sending agent messages or storing request contents. Disabled, unavailable and older workers without MCP status are shown explicitly.

### Client setup states

The **Coding agents** group has one row for Claude Code, whose CLI and VS Code extension share one configuration, and one row for Codex. The tray carries the same rows as one item per client. Each state in a row comes from its own evidence:

| State | Evidence |
|---|---|
| Broker | The worker's status: running, running in another companion (standby), or not running. |
| Configuration | **Check client setup** runs the client's read-only `mcp get` for the `desktop-ai-companion-agentbroker` entry only: `claude mcp get <name>` or `codex mcp get <name> --json`. It reports the exact entry for this broker (for HTTP, its literal or its localhost URL) with its effective scope and transport, an absent entry, an entry under that name that points elsewhere, an entry the client reports rejected or disabled, a managed-policy refusal, a CLI that was not found, or a report this version does not recognize. Codex reports no scope. |

An inbox counts for a client only when its own `register_agent` request carried that client's identity (in `initialize` for that request, or 2026 per-request metadata). | Native | The client's discovery and wake switches, its adapter's reported errors and its discovered native sessions. |

The configuration check runs only when asked: from the pane, from the tray, or after **Connect Claude MCP** or **Connect Codex MCP**. The two-second status poll never starts a vendor CLI. Claude's `mcp get` makes its own connection to the configured entry, which is why the Claude row can report the endpoint reachable. The check never reads or writes a client configuration file and shows fixed states only, never CLI output. A settings change clears the previous check, because it compared the entry with the old port and paths. The companion finds `claude.exe` or `codex.exe` by the same rules as its model calls (see Setup) and starts that binary itself. An npm `claude.cmd` or `codex.cmd` shim is never run, only resolved to the binary it would start; CLI not found means no rung of that order holds the client. The tray item for a client whose entry is absent also offers its Connect action.

If settings change while a setup action is running, the pane preserves its sanitized action result and asks for another check. That old action does not update the new connection's cached status or notifications. Run **Check client setup** before deciding whether to retry.

### Pairing and deadlines

When a broker is discovered, the companion asks before requesting pairing. Compare the complete code on both machines and explicitly approve on both. A request or a single approval grants no sharing. Pairing authorizes both brokers' current and future discoverable sessions. The tray exposes private, mute and revoke controls. If multicast discovery is blocked, copy a public broker invitation from one options pane and paste it into the other, then use the same pairing-code approval flow. Invitations contain public identity information only.

Simultaneous requests previously left two offers with different comparison codes on each broker. A deterministic HTTPS regression reproduced that failure before the fix. A collision now keeps the lower broker identity's outbound offer and retires the other request, nonce and code. Repeated requests for an exact pending peer reuse its current offer. Both users must still approve the same complete code; approval of a discarded code never transfers. The companion withdraws an obsolete comparison question and ignores a late response to it. A collision displays current-code guidance rather than a connection failure, with no automatic retry or authorization.

Pairing requests and confirmations use a 30-second control-client deadline around the worker's 25-second operation deadline. A request can perform two HTTPS exchanges, each bounded to ten seconds. Ordinary status retains its three-second client deadline. Network, TLS and rejected-offer failures remain visible in the Pairing information, tray and pinned failure status after healthy status polls. A saved pairing for the same broker ID and certificate clears its obsolete pairing failure, while errors for other identities remain. The pane and tray show saved trust separately from current reachability. Guidance uses fixed error categories without raw remote diagnostics. If a result is lost, inspect pending or paired brokers before retrying; a timed-out reply does not prove that no state changed.

The **Paired brokers** list beneath **Status** shows saved broker names and HTTPS endpoints. It updates with status, including endpoint changes, and distinguishes an empty list from an unavailable worker. Saved trust does not establish current reachability. A successful pairing remains visible after restarting the worker; delayed status responses cannot replace a newer pairing or revocation observation.

Both workstations must be able to reach the configured HTTPS port. Automatic discovery also needs UDP 5353 on the local network. In the AgentBroker settings pane or tray menu, choose **Allow LAN access** after this companion's own LAN worker reaches Running. The companion asks for consent, then requests Windows administrator approval. Its fixed-purpose worker command adds an inbound allow rule for that exact executable and applied TCP port, limited to the Private profile and LocalSubnet, with edge traversal disabled. It adds no Public-network rule, changes no existing rules and configures no router port forwarding. Run the action on each workstation that needs inbound access. Changing the applied port or installation path needs another setup action; previous rules are not removed automatically.

Setup verifies the requested rule and reuses an identical existing rule. Conflicting rules, possible application block rules and policy restrictions are reported for review rather than edited. An allow rule alone does not prove reachability: other firewall rules or network policy can still block the connection. A timed-out or interrupted Windows setup has an unconfirmed outcome, and another action waits for the original elevation operation to finish. The management pipe remains local, and pairing still requires both brokers' explicit approval. A physical second-workstation test remains necessary to validate a particular LAN's routing and firewall configuration.

**LAN firewall access** also shows three separate readings. The network category (Public, Private or Domain) is the one Windows applies to the interface carrying the broker's advertised LAN address, read through Network List Manager without administrator rights. The firewall rule state is this worker's own rule as Windows Firewall lists it: configured for the Private profile, absent, or a different rule under its name. When the network is Public or Domain and the rule covers Private networks only, one sentence explains why other PCs cannot connect. AgentBroker never changes a network category and never adds a Public-network rule. **Observed** says whether an HTTPS request from another private address has reached the LAN listener since the worker started. A configured rule is not observed reachability, and a request from this PC to its own address does not count. The category and rule are read in the background and reused for a short interval (`LanProfileMonitor.MaximumAge`), so a status request never waits for them.

Discovery checks private IPv4 interfaces every ten seconds, retries while offline, and recreates sockets after interface changes or transport failures. Pairing survives worker restarts and reboots when each broker keeps its Windows user, data directory and identity. A paired broker keeps using its saved address while that address works. If discovery announces a changed private IPv4 HTTPS address, automatic recovery verifies the original broker ID and paired public identity over HTTPS before saving the new endpoint. The original approval, identity pin and name remain unchanged. Since 1.9.0, a renewed TLS certificate can prove continuity with that original pin using the same private key. Discovery cannot create trust or restore a revoked pairing; a replaced identity requires explicit pairing again.

A read-only LAN probe successfully reached a discovered peer's pinned HTTPS public-info endpoint without pairing approval or agent input. Later historical physical two-workstation tests passed message delivery, acknowledgement and correlated replies on 2026-11-02; Claude native wake and its reply also crossed the pairing. The dated receipts are retained under `N-agentbroker-two-pc-01` in [BLOCKED.md](BLOCKED.md) and in the [1.8.0 wake-subpoint record](agentbroker-180-validation.md#wake-subpoints-and-backlog-burn-down-audit). These successes do not establish every physical restart, reboot, DHCP or revocation case, or repeat acceptance for the current package. The synthetic HTTPS collision smoke and full network regression remain separate evidence.

## Agent tools

The MCP server exposes `whoami`, `register_agent`, `list_sessions`, `send`, `wait_for_receipt`, `wait_for_reply`, `wait_for_messages`, `acknowledge_message`, `reply_to_message`, `read_inbox`, `read_inbox_page`, `read_native_recovery`, `set_session_declaration`, `set_session_title`, `get_message_receipt` and `send_message`. Every `initialize` result carries the short instructions card in `BrokerInstructions.cs`, forwarded unchanged by the stdio bridge. Use complete addresses and stable message IDs. A native submission is not proof that the recipient received it; explicit acknowledgement remains separate from work completion.

The optional [Claude custom-title hook](agentbroker-claude-title-hook.md) adds documented custom titles to local directory rows. Generated titles are unavailable through that hook. Titles and manual declarations are display hints; neither changes an address, grants predecessor rights, or reaches a paired broker.

| Tool | Parameters and defaults | Result | Refusals beyond address and broker checks |
|---|---|---|---|
| `whoami` | none | The caller's own native `claude:` or `codex:` directory row | `no_native_session`, `caller_elevated`, `caller_unresolved`, a connection that is not local loopback |
| `send` | `sender`, `recipient`, `messageId`, `text`, `conversationId` (defaults to `messageId`), `ttlMinutes` (0 means the default lifetime; longer values are capped at 24 hours) | The sender's receipt, without the text (see below); a retry returns the original one | `message_id_collision`, `sender_unavailable`, `recipient_unavailable`, `invalid_message`, `reserved_message_id` (a `messageId` in the notice ID space), `reserved_session`, a negative `ttlMinutes` |
| `wait_for_messages` | `session`, `timeoutSeconds` 20 (0..25), `limit` 16 (1..16) | Incoming receipts still `Accepted`, oldest first; empty means the deadline passed | `wait_in_progress`, `wait_capacity`, `session_unavailable`, out-of-range values |
| `wait_for_receipt` | `messageId`, `timeoutSeconds` 20 (0..25) | That message's receipt, without the text, as soon as it is `Delivered`, `Held`, `Refused`, `Expired` or `Uncertain`; at the deadline, its current receipt (`Accepted`, `Submitting` or `Submitted`) | `wait_in_progress`, `wait_capacity`, `session_unavailable`, a missing or foreign original |
| `wait_for_reply` | `messageId`, `timeoutSeconds` 20 (0..25), `unacknowledgedOnly` false | Replies to that message addressed to its sender, oldest first, at most 16; true excludes acknowledged history and expired messages | `wait_in_progress`, `wait_capacity`, `session_unavailable`, a missing or foreign original |

### Receiving during active work

`read_inbox_page(session, cursor, limit)` fetches pending messages without blocking or taking a wait slot. It works on the existing exact native address while its turn remains active; it does not inject into that turn, create a mailbox, or start a background poller. `limit` defaults to 16 and must be 1 through 16. Each `entries` element contains an `arrivalSequence` and a complete `receipt`. The result also contains `pendingCount`, `hasMore`, and `nextCursor`. Pending means an unexpired incoming message still `Accepted`, `Submitting`, `Submitted`, or `Uncertain`; `Held`, `Delivered`, and `Refused` are already acknowledged and omitted. Reading acknowledges nothing. Retain the content before acknowledging it, and handle each message ID once if wake or another fetch also supplies it.

Start without a cursor, retain each page's content, and continue with its opaque `nextCursor`. Unlike the legacy `read_inbox` GUID cursor, this cursor can be retained between polls: new arrivals receive larger broker-assigned sequences, even when their UUID or sender-supplied creation time sorts earlier. `pendingCount` counts all pending messages for the address, including earlier arrivals already passed by the cursor. An empty incremental page can therefore have a positive pending count. Start again without a cursor when those earlier messages need rereading.

The sequence index lives only for one worker opening and is rebuilt from the durable snapshot's acceptance order. `inbox_cursor_reset_required` means the worker restarted: discard the cursor, rescan without one, and deduplicate by message ID. `invalid_inbox_cursor` refuses malformed, unsupported, wrong-address, or future cursors. `session_unavailable` requires refreshing native discovery, or re-registering the same generic mailbox identity. No cursor adds ownership or recovery rights across incarnations. Legacy `read_inbox` retains its history ordering, and schema-1 persistence is unchanged (`src/AgentBroker.Core/PendingInbox.cs`). Since 1.10.0, MCP inbox, incoming-wait and acknowledgement responses explicitly include `replyTo: null` for non-reply `BrokerMessage` values. Recovery entries also include `blockReason: null` when unblocked. This additive null output follows the published required-nullable schema; durable and federation serializers are unchanged (`McpToolJson.cs`).

Successful local operations that establish an exact participant append an `agentbroker.pending_messages` JSON advisory after their existing content blocks. It supplies the exact `session`, `status`, `pendingCount`, and `fetchTool`. The original first block stays unchanged; `send` keeps its existing generic-mailbox advisory too. An unavailable count is explicitly `status: unavailable` with `pendingCount: null`, never zero. A shared Codex transport cannot identify one chat, so operations with no unambiguous participant, such as `list_sessions` and `get_message_receipt`, receive no session-specific hint. The hint is a fresh observation after the operation, so concurrent arrivals can make it newer than the operation's own result (`BrokerTools.Inbox.cs`, `McpActivityTracker.cs`).

### Native session recovery

`read_native_recovery(session, cursor, limit)` inventories the retained incoming and outgoing records of the current native conversation, including earlier incarnations. The current address must have been observed by its matching `claude-native` or `codex-native` adapter, must still have that discovery lease, and must support receiving. A generic registration, matching label, native-looking ID, or direct registration cannot establish this authority. Local access remains broker-scoped; this feature does not authenticate which Codex chat owns a shared client connection (`NativeRecovery.cs`, `BrokerRuntime.cs`).

Each entry preserves the original receipt, sender, recipient, message ID, conversation ID and `replyTo`. It reports the incoming/outgoing relationship, earlier incarnations and retained-content availability. `canAcknowledge` and `canReply` describe ordinary operations for the current exact recipient only; both are false for a predecessor's records. Acknowledged tombstones retain metadata without their original text. Current privacy and revoked peer trust suppress peer content and actions.

The opaque cursor orders records when the local inventory first observes them; it does not reconstruct historical arrival order for tombstones. It can continue to newly observed records between calls. Start without a cursor to refresh changed statuses, availability and action fields of records already seen. A worker restart or privacy/trust policy change explicitly returns `native_recovery_cursor_reset_required`; discard the cursor and rescan. Queries are bounded to 1 through 16 entries, and recovery indexing is lazy on explicit inventory reads rather than scanning tombstones on each ordinary commit.

Recovery is report-only. A successor cannot acknowledge, reply as, or reactivate its predecessor. After inspecting retained content and receipts, an authorized agent may continue with an explicit new `send` between current complete addresses, using a fresh message ID and a conversation reference when useful. Recovery does not grant permission to repeat an old task.

New sends and replies still require an addressable exact recipient. The broker does not hold a new reply for an absent native requester or route it to a successor. When fresh matching native discovery proves a replacement incarnation, delivery re-evaluation refuses its predecessor's never-submitted Accepted mail as `recipient_replaced` and uses the existing exact-sender notice path. A lease lapse alone does not establish replacement. Submitting, Submitted and Uncertain mail is preserved because it may have reached native input.

Fresh verified native calls receive `recoveryPendingCount` and `recoveryTool` in their pending advisory. That count describes pending incoming messages addressed to earlier incarnations, not the whole retained recovery inventory or any action rights. Recovery has no automatic wake; the current native session calls explicitly. No payload is retargeted or uncertain submission reinjected. Inbox and recovery tools publish output schemas and `structuredContent` while preserving complete JSON in `content[0]`.

### Your own address

A Claude Code or Codex session the broker discovered natively has a directory row of its own (`claude:<session ID>` or `codex:<thread ID>`). When that row has `Receive` and `WakeIdle`, a message to it wakes the session when it is idle, so the session sends as that address and gives it to peers, without a duplicate mailbox or heartbeat. While the native session remains active, it can fetch pending messages explicitly with `read_inbox_page` using that same exact address. A row without them is observation-only (native delivery is off, or the client build is not reviewed and is not carried by its client's "Also wake updated ... builds" switch, which is on by default and needs the publisher's verified signature): replies to it are refused as `recipient_cannot_receive`, so such an agent registers a mailbox for replies. `whoami` returns the row either way, unchanged. The broker finds the process that owns the client end of the caller's loopback connection, walks up its parent processes, and returns the session a native adapter binds to the nearest `claude` or `codex` process. The match is by process ID and exact creation time, so a reused ID never matches (`tools/AgentBroker.Worker/CallerProcess.cs`, `BrokerRuntime.WhoAmI`). The walk stops at the nearest `claude` or `codex` process even when that process is no discovered session, so an agent started by another agent (`claude -p` inside a Claude session) is never told it is its parent. A Claude process hosts one session, so a Claude caller resolves whenever its session is discovered. A Codex caller never resolves to a row: it gets `no_native_session` (or `caller_elevated` when it runs elevated, as any caller does), because one Codex server process hosts every chat of its window, including chats discovery has not seen or whose observation aged out, so the server process never proves which chat is asking. An earlier draft named the one discovered chat on a server; Codex session 01a1855c's review showed that could return another chat's row. Without `whoami`, a Claude Code shell has its session ID in `CLAUDE_CODE_SESSION_ID`, and its row is the one whose `sessionId` is `claude:` followed by that value. A Codex shell has its thread ID in `CODEX_THREAD_ID` (a Codex VS Code chat, extension 26.1021.22027, reported it on 2026-10-29), and its row is `codex:` followed by that value. That is how a Codex agent finds its own row.

An elevated agent (a Claude Code or Codex session run as administrator) gets `caller_elevated`, not `caller_unresolved` or `no_native_session`. The broker runs at Medium integrity, and Windows refuses it part of the access to an elevated process, in one of two shapes. A same-user UAC elevation, as measured on one workstation, allows the limited query and refuses the full one (`PROCESS_QUERY_INFORMATION`), so the walk reaches the elevated claude process, which no adapter binds, and its refused full query answers (`QueryDenied`, asked of the nearest claude or codex process only). A process of another user, or a protected one, refuses even the limited query, so the broker finds the connection's owner but cannot walk it (`WindowsCallerProcessResolver.Compose`); that shape is handled by design and was not measured as a same-user elevation. Either way the broker cannot verify or wake the session. That is deliberate and not bridged: a broker able to drive an elevated session would let any Medium process drive one. Such an agent registers a mailbox with `register_agent`, or runs unelevated. Claude discovery skips the same session (its image cannot be read) and says so in Status as a count, `claude_session_elevated`, naming no process, session or path (`ClaudeNativeProvider.RefreshCoreAsync`): a note shown on its own line beside the healthy sessions' wake line, not an adapter error that would replace it. Until 1.7.0 it was skipped in silence. `caller_unresolved` still means no owner was found.

An agent with no native row registers a mailbox and sends its first message to the peer's native row, which wakes the peer, then waits with `wait_for_messages`.

Incarnations change. A Claude session gets a new one when its process restarts. A Codex chat's incarnation is the conversation on its running Codex server process (`codex-thread-v2`), so it changes when that process restarts, not when a view reconnects or another view takes ownership; each delivery still targets the owner rediscovered for that attempt. Until 1.4.0 it also covered the owning view, and on 2026-10-29 two new chats changed address within minutes of opening, which stranded queued messages and broke acknowledgements and replies to them. Upgrading to 1.4.0 changes every Codex address once. A send to an old incarnation is refused as `recipient_unavailable`. Read `list_sessions` again, or ask the peer to call `whoami`, and send again.

A Codex row also says which engine holds its thread, as a report only (owner's decision 2026-10-30): `engineBinding` on the `list_sessions` row, and on the sender's receipt what was observed at the message's latest attempt. The adapter asks Windows Restart Manager who has the thread's writer lock open (`%USERPROFILE%\.codex\thread-writer-locks\<threadId>.lock`), read-only, in the background after each discovery pass and within a budget (`tools/AgentBroker.CodexDesktopAdapter/CodexEngineBinding.cs`). A row the budget did not reach keeps its previous observation, whose `observedAt` says how old it is. A delivery's receipt carries the latest observation of its row, so no query sits between the owner re-check and the write. `bound` with `code_engine` or `desktop_engine` means exactly one holder, a codex.exe whose process ID and start time are a Code-owned engine's or the Codex desktop app's. Otherwise it is unbound with the reason: `lock_missing`, `lock_path_reparse` (a reparse point on the path, reported and never followed), `query_failed`, `no_holder`, `multiple_holders`, `foreign_holder` or `start_time_mismatch`. A codex.exe that cannot be read (it exited, or belongs to another user or an elevated VS Code) affects only a lock it holds, which reads `query_failed`. Nothing is refused, deferred or re-addressed on it, and a paired broker never receives it, neither on a row nor on a receipt. The Codex client's status in the AgentBroker pane counts bound and unbound rows by reason. Which webview of a window answered an owner lookup stays unverifiable, a limit of the vendor's router (`docs/DESIGN-REGISTER.md`, feature/broker-163).

This section and `whoami` exist because, on 2026-10-28, two agents on a second workstation registered mailboxes and one ran a 30-minute poller, although that one had a native row, and the owner carried one agent's address to the other by hand.

### Display hints

Display hints use the existing exact native address. `set_session_declaration` requires a current adapter-verified native row with Receive; `set_session_title` requires a canonical `claude:` row, so a `codex:` title is refused. Empty values clear a hint. `native_session_unverified`, `invalid_session_declaration`, `declaration_limit`, `invalid_session_title` and `session_title_limit` carry fixed recovery guidance pointing to `list_sessions`. Correct invalid values using the tool's bounds, or clear a hint you set when capacity is full; registering another session does not bypass those limits (`BrokerTools.Declarations.cs`, `BrokerTools.Titles.cs`, `BrokerRecoveryGuidance.cs`).

### Mailboxes and retention

A generic MCP registration has two lifetimes. Its presence lease lasts one minute, and every successful call that names the session renews it: reads, waits, sends, replies and acknowledgements. When presence lapses, the mailbox stays addressable for 24 hours after the owner's last call, provided the agent keeps the same `clientId` and incarnation. A retained mailbox still accepts sends and replies from local agents and paired brokers. Its owner can still read, acknowledge and reply, and the owner's next successful call restores presence. A new incarnation is a new mailbox.

A present mailbox lists as `Idle` only while its owner is inside a wait (`wait_for_messages`, `wait_for_reply` or `wait_for_receipt`) and as `Unknown` otherwise, for local callers and paired brokers alike. Registering or renewing proves nobody reads the inbox; on 2026-10-28 a mailbox nobody had read for hours looked live to its senders. The store still records a present mailbox as `Idle`; only the directory view changes (`BrokerStore.PresentedDirectory`, which both `list_sessions` and `/federation/directory` serve). A local `list_sessions` lists a retained mailbox with `Activity` `Away` and its last, now past, `LeaseUntil`. Paired brokers, the peer directory and `/federation/directory` still list present sessions only, so `Away` never leaves this broker and no federation record changed. Native sessions keep the live-lease rule: once a native lease lapses, ordinary sends from or to it are refused. A registration cannot claim `Away` itself.

Retention is process-local and never persisted. A worker restart drops every registration while messages persist, and registering the same `clientId` and incarnation again finds them. At most 64 mailboxes are retained. A registration that would pass the 256-session bound takes the slot of the oldest retained mailbox with no outstanding message, then of the oldest retained one, and never a present session's. A local privacy or pause choice applies to a retained mailbox without restoring its presence.

### Waiting instead of polling

`wait_for_messages` returns at once when the session has incoming messages still `Accepted`, meaning not yet acknowledged. Otherwise it blocks until the store records a change or the deadline passes, then checks again. Acknowledge each message actually received, or the next wait returns it again. `wait_for_reply` waits the same way for replies to one message the caller sent; one message can receive several replies.

A recipient's acknowledgement never arrives in the sender's inbox, so a sender that wants to know whether its message was received uses `wait_for_receipt` (or polls `get_message_receipt`). It returns as soon as the receipt is `Delivered`, `Held`, `Refused`, `Expired` or `Uncertain`. `Submitted` only means a native adapter or a paired broker admitted the message for transport, so the wait continues until the recipient's own receipt, a refusal or the deadline. A receipt read after its message's deadline shows the deadline's outcome at once, by `get_message_receipt` and `wait_for_receipt` alike, rather than after the next delivery pass: `Accepted` and `Held` become `Expired`, `Submitted` becomes `Uncertain`, and `Delivered` and `Refused` stay as they are. A waiting `wait_for_receipt` also wakes at the message's deadline by itself, so it does not depend on another commit to notice the expiry. An `Accepted` message to a native session that has not been tried yet names its wait in the receipt's reason, read from the recipient's present state: `recipient_busy`, `recipient_awaiting_approval`, `recipient_interrupted`, `recipient_activity_unknown`, `recipient_wake_unavailable` (the row lists `Receive` without `WakeIdle`), or `recipient_unavailable` (its row lapsed or is gone); a message that was tried and deferred keeps that deferral's reason, such as `native_context_busy` (`BrokerStore.WithWaitReason`). A Codex row whose engine check could not complete lists `Receive` alone for up to five minutes, so messages to it wait instead of being refused and are delivered once a discovery pass completes the check; past that its queue is refused `recipient_cannot_receive` (`CodexNativeAdapter.DiscoverAsync`). On 2026-10-28 a sender asked to "poll for my acknowledgement" waited 25 seconds on its own inbox each time, while the acknowledgements came 3.5 and 8 minutes later and never appeared there.

The receipts a sender gets back (`send`, `send_message`, `reply_to_message`, `wait_for_receipt` and `get_message_receipt`) leave out the message text, which every poll used to hand back to the agent that wrote it, up to 16 KiB each time (`tools/AgentBroker.Worker/SenderReceipt.cs`). They keep the receipt's own nested shape (`message.id`, `message.sender`, `message.recipient`, `status`, `reason`, the times and `attempts`), so a client that read those reads them unchanged. `textBytes` is the text's length in UTF-8 bytes, or null once the broker no longer holds it (a tombstone); `get_message_receipt` with `includeText` true returns the text. The tools a reader uses (`wait_for_messages`, `read_inbox`, `wait_for_reply`) still carry it. Each receipt also tells its own age: `engineBinding` is the Codex engine report described above, as observed at the message's latest attempt. A paired broker's caller gets neither `busySince` nor `engineBinding`: both are this workstation's observations of its own processes. `readAt` is the broker's clock at the read, so `readAt` minus `updatedAt` is how long a `Submitted` or `Held` receipt has held its status, or how long ago an `Accepted` one was last tried. A deferred message's `busySince` starts at the first busy answer in its current run (`native_context_busy` or `native_recipient_busy`). An `Accepted` receipt waiting on `recipient_busy`, or a `Submitted` receipt, can instead carry the first fresh directory observation of its native recipient being Busy. These are observations of availability, not progress on the requested work. `busySince` and the delivery observations behind it live in the worker process only: `broker-state.json` keeps the schema an older worker reads, and a restart starts them again (`DeliveryObservations`). A native row that discovery can only call `Unknown` is listed `Busy` while its recipient was observed busy within the last 30 seconds. That is presentation in the local `list_sessions` only: the stored activity, which decides when a message is tried, is unchanged. A peer session reported a Codex recipient's receipt that sat `Accepted` / `native_context_busy` for about two hours while its row read `Unknown`, and two others sat `Submitted` with nothing telling their age.

A wait releases the store lock before awaiting a signal. Every committed change completes a signal, and a waiter captures that signal before it checks, so a message committed between the check and the wait still wakes it. Waits are local operations. Each session has at most one active wait per class (`wait_in_progress`): `wait_for_messages` and `wait_for_reply` share the incoming class, because both return the same `Accepted` reply and a second would only race the first for it, while `wait_for_receipt` returns no message and has its own receipt class, so it may run beside an incoming wait. The worker allows at most sixteen waits across every class (`wait_capacity`). A generic mailbox lists as `Idle` while any of its waits is active, until the last one ends. The 25-second bound stays inside the stdio bridge's 60-second request limit and ordinary client tool timeouts, so no client needs a longer timeout configured. A wait on a mailbox that nothing can reach is refused as `session_unavailable` instead of returning empty indefinitely. That covers a session never registered, one past its retention, and one lost to a restart. The refusal comes before anything is returned, even while messages are pending for that mailbox: `acknowledge_message` refuses them until the owner registers again, so a restart-lost mailbox's kept messages come back from the first wait after `register_agent` with the same `clientId` and incarnation. `wait_for_reply` applies the same rule to the original sender's mailbox.

Address removal completes the same change signal used for committed messages. A quiet native lease or generic mailbox's retention can end without a mutation, so waits also wake at that exact addressability deadline. They do not periodically reread retained message history. On worker shutdown, wait admission closes before HTTP draining and active waits receive `broker_stopping`. Reconnect after restart, refresh the exact session address and inspect existing receipts before retrying a message.

### Sending

`send` builds the message from the fields the caller supplies. A retry with the same `messageId` compares the sender, recipient, text, the absence of a reply parent and, when given, `conversationId`. It never compares timestamps. A match returns the original receipt unchanged and ignores `ttlMinutes`; any difference is `message_id_collision`. That holds after the recipient acknowledged the message too, when the broker compares the text by its SHA-256 (see Acknowledged messages). `send` returns its receipt as the first content block, in the shape `send_message` returns. When the recipient is a local generic mailbox that nothing can wake (`Receive` without `WakeIdle`), a second text block says so: the mailbox sees the message only when its owner next waits or reads its inbox. A recipient on a paired broker gets no advisory, since this broker does not know its capabilities at send time (added in 1.4.1, `BrokerTools.SendTool`). `send_message` is unchanged for callers that need to supply the complete record, and its retries must therefore repeat the original timestamps.

### Reply budget

Every message carries `remainingReplies`. A `send` starts at 8, and a reply gets one fewer than the message it answers, so one chain of replies allows eight. `reply_to_message` on a message at 0 is refused as `reply_budget_exhausted`. To keep talking, `send` to the same peer with the same `conversationId`: the conversation keeps its ID and the new message starts at 8 again. The budget exists so two agents cannot answer each other automatically without end. It cannot be raised, because a paired broker refuses a message whose budget is above its own maximum of 8 (the `RemainingReplies` checks in `src/AgentBroker.Core/BrokerStore.cs`). The native envelope's preamble, the card and the `reply_to_message` description say this, because on 2026-10-28 agents on a second workstation started fresh conversations at the eighth reply.

`list_sessions` and `read_inbox` return arrays in bounded pages. Both accept an optional `limit`, defaulting to 16; values outside 1 through 16 are refused. A full page may have more results: call again with the last returned key as the cursor. A shorter or empty page completes that scan.

| Tool | Cursor for the next page | Ordering |
|---|---|---|
| `read_inbox(session, limit, afterMessageId)` | Last receipt's `message.id` | Message GUID comparison |
| `list_sessions(limit, afterAddress)` | Last session's complete `address` | Broker GUID, ordinal session ID, incarnation GUID |

Copy cursor values from the last result rather than constructing an offset or looking up the old record. An expired inbox record or disconnected session does not invalidate its key. These collections are mutable live views, not snapshots: new messages or sessions may appear before an existing cursor. Start each new poll without a cursor and finish its pages before polling again. Paging keeps large retained inbox histories within the stdio response limit without truncating message text.

### Acknowledged messages

Once a message sent from this broker is `Delivered` or `Refused`, whether by `acknowledge_message`, a native adapter's receipt or a paired broker's, the broker drops its text and keeps a tombstone: the message ID, a SHA-256 of the text, the sender, recipient, reply parent, conversation, reply budget, status, reason and times (owner decision 2026-10-27). What needs no text keeps working. A `send`, `send_message` or reply retry with the same ID and text returns the original receipt, and different text is `message_id_collision`. `get_message_receipt`, `read_inbox` and `wait_for_reply` show the message with its status and an empty `text`; real message text is never empty, so an empty one always means the broker no longer has it. A late `reply_to_message`, and `wait_for_reply`, on an acknowledged original still route. `acknowledge_message` answers with what the broker now keeps, so read the text before acknowledging.

Three kinds of message keep their text until their record goes. `Held` is not final: it can still become `Delivered`, `Refused` or `Expired`. `Expired` was never acknowledged, and its recipient can still read it. A message from a paired broker keeps its text because that broker settles its receipt by fetching it and comparing the whole message, text included, with its own copy. For the same reason `/federation/receipts/{id}` answers a tombstoned ID with 404, exactly as an unknown one, and never sends a receipt without its text.

Tombstones are kept in `broker-tombstones.jsonl` beside `broker-state.json`, one line each, and leave one day after their message expires, as a full receipt does. Only messages that still carry their text count toward the 4,096-message bound. Tombstones and those messages together are bounded at 65,536, so an acknowledgement always has room, and a send past that bound is refused as `message_limit` rather than dropping a tombstone. At the default 24-hour lifetime that sustains about 22 acknowledged messages a minute, where receipts with text sustained about 1.4. The measurements are in DESIGN-REGISTER under `feature/agentbroker-backlog-e`.

`broker-state.json` keeps the exact shape a 1.0.4 worker reads and holds only messages that still have their text, and 1.0.4 never opens the tombstone file. A rollback to a 1.0.4 worker therefore loads the data and loses only the tombstoned IDs: their receipts are unknown, a retry of one is admitted as a new message and delivered again, and a reply to one is refused. Starting this version again turns anything 1.0.4 acknowledged meanwhile into tombstones.

### Delivery notices

A new local `Held` transition at or after the message deadline is refused as `message_expired`; an existing identical receipt remains idempotent. A late `Delivered` or `Refused` can still settle a Submitted or Uncertain record. Held does not extend its deadline, and paired receipts retain their existing reconciliation path (`BrokerStore.RecordReceipt`). A notice itself cannot be answered: `reply_to_message` refuses it as `notice_reply_refused` and points to `acknowledge_message`. Recipient acknowledgements, replacement refusals and peer-prefixed reasons keep their specific explanations. Otherwise-unclassified refusals for a remote recipient name its paired broker and ID (`BrokerStore.NoticeText`, `BrokerRecoveryGuidance.cs`).

Since 1.10.0, a local sender also receives an advisory when its message becomes `Uncertain`, including an interrupted submission recovered after restart. It names the original exact address, event time and reason. This is historical delivery information: the current receipt may already have changed. Inspect it with `get_message_receipt` and check with the recipient before choosing any new send. The broker never resends automatically, and Delivered still means receipt rather than work completion. An uncertainty advisory has an independent ID derived from the source lifetime; its retained record or tombstone prevents repeat advisories after restart or acknowledgement. An advisory not yet admitted is cancelled if the source resolves. An admitted advisory remains historical. Terminal notices retain their existing IDs. If a delayed terminal notice outlives its source, that source UUID remains reserved until the notice's ordinary retention ends (`message_id_collision`); retained-source retries still recover their original receipt. No source retention is extended (`BrokerStore.WithSenderNotices`, `RebuildOwed`, `SenderNoticeId`, `NoticeText`, `Accept`).

When a message sent from a session on this broker ends as `Expired` or `Refused`, the broker puts one notice in that sender's own queue. A native sender is woken with it like any other message; a generic mailbox's `wait_for_messages` and `read_inbox` return it. The notice comes from the reserved address `agentbroker:notices` on this broker. Its text names the message's ID and conversation, its recipient (with that session's label when the recipient is still registered as the notice is admitted; labels are not stored), when it was sent, and what happened. For an expiry it gives the delivery deadline and the number of delivery attempts, and says the deadline passed without a `Delivered` receipt: the broker cannot tell whether the recipient read the message, because a generic recipient can read one it never acknowledges. A native session receives the notice framed as an `agentbroker.delivery_notice` from the broker, not as an agent's request. Acknowledge it like any message. Nobody can reply to it, and a notice that itself expires produces no further notice.

This exists because, on 2026-10-28, two messages sent with a 20-minute lifetime to a generic mailbox whose owner never read it expired with zero delivery attempts, and their sender was never told. A native session is also delivered to only while it is idle, so a short lifetime can run out while its owner is busy.

A notice is owed to the sender's exact address (session ID and incarnation) until that address can take it: addressable, able to receive, with fewer than 64 messages outstanding, and within the store's message bounds. Each delivery pass admits owed notices whose sender is back or has room. Passes come about every half second while the four delivery loops are idle, and later while all four are busy submitting to native sessions, which can take up to 20 seconds each. A notice always gets the maximum 24-hour lifetime, whatever the configured default, and it starts when the notice is admitted, not when it became owed. After a broker restart, the first delivery passes can commit expirations before discovery has re-registered the native sessions; those notices arrive once each session is rediscovered. What is owed is derived from the durable receipts, not kept only in memory: when the broker starts, every `Expired` or `Uncertain` record and `Refused` tombstone of a message a local session sent, whose notice exists neither as a record nor as a tombstone, is owed again, so a restart loses no notice. A notice is sent only while its source receipt is retained, which is until one day after the message's deadline. One that cannot be admitted by then is dropped, never sent late: that happens when the sender stays unavailable that long, or when the store, or the sender's queue, stays full that long. Room is counted as the commit will leave it, including the tombstones that commit writes, so a notice never pushes the store past a bound it could not reopen with. Messages the broker prunes during downtime of more than a day past their deadline produce no notice. On the first start of this version, senders are owed notices for their messages that ended without one and whose receipts are still retained. A refusal's receipt is kept until one day after that message's deadline, so it can be almost two days old. The burst is bounded by those retained receipts and by the admission limits above. A message from a paired broker produces no notice here; its own broker settles it. For a message this broker sent to a paired broker, a verified `Expired` there is recorded as `Refused` with reason `peer_expired`, and the notice says it expired at the recipient's paired broker without a Delivered receipt; until 1.4.1 it was recorded as `recipient_receipt` and the notice said the recipient had refused it (`BrokerStore.RecordPeerReceipt`). No session can register as, send as, or send to `agentbroker:notices` (`reserved_session`). Terminal notice IDs are derived from the original message's ID as version-8 GUIDs that carry a fixed 32-bit marker. The broker refuses any newly submitted message whose ID carries that marker (`reserved_message_id`), so no new message can take a notice's ID and suppress it. Records stored by an earlier version are not checked: an earlier version accepted any caller-chosen ID, and a retry of such a message whose ID happens to carry the marker is refused too. Other version-8 IDs stay usable; the channel bridge derives its reply IDs that way. A notice's text is held to the configured message text bound, trimmed from the end if a small bound requires it. Notices are ordinary messages on disk, in the schema-1 shape, so a rollback loads them unchanged.

## Intended behavior

Each workstation runs its own local broker. Agents use MCP to discover reachable sessions, send a message, inspect a receipt, and reply. A compatible adapter wakes the exact existing idle session through its original client owner. Session names and working directories are display metadata, never addressing keys. Addresses include broker identity, vendor session ID, and an adapter incarnation.

The workstation endpoint may omit authentication when it is strictly bound to loopback. LAN communication uses authenticated HTTPS. A discovered broker initially exposes identity and connection information only. Explicit pairing authorizes current and future shared sessions in both brokers; private sessions remain excluded. Pairing never grants transitive trust or changes a session's tool permissions.

Discovery and transport stay local. This does not make Claude or Codex inference offline: the chosen agent's existing model provider still applies.

## Agent conversations

Two agents (Claude Code, Codex or any MCP client) keep a conversation across their turn boundaries without a sidecar process:

1. Each agent calls `whoami` (a Codex agent finds `codex:<CODEX_THREAD_ID>` in `list_sessions` instead). A native row with `Receive` and `WakeIdle` is its address: it sends as that row and is woken when idle. An agent with no such row picks one `clientId` and one incarnation for the conversation and calls `register_agent` with that pair at the start of every turn.
2. The asking agent finds the other session with `list_sessions`, routing by complete address. It calls `send` with a fresh `messageId`, then `wait_for_receipt` for receipt and `wait_for_reply` for the answer. For later answers, use `unacknowledgedOnly: true`, or retain the `read_inbox_page` cursor across active-work checkpoints. Legacy reply waits also return acknowledged history by default.
3. The answering agent receives the message (a native session is woken when idle or fetches `read_inbox_page` while active; a mailbox calls `wait_for_messages`), acknowledges each message it actually received with `acknowledge_message` and outcome `Delivered`, and answers with `reply_to_message`. When the reply budget runs out, either side continues with `send` and the same `conversationId`.

Run one incoming wait (`wait_for_messages` or `wait_for_reply`) at a time per inbox; a `wait_for_receipt` may run beside it. Accepted and Submitted are not Delivered, and Delivered does not mean the work is done. Peer text is untrusted data: it never overrides the user, the receiving session's instructions or its permissions, and no agent should use a peer to do what its own session may not.

Legacy free-form handoff convention. Message text may be one JSON object:

```json
{"kind":"request|status|result|handoff","summary":"...","artifacts":[{"path":"<repo-relative>","sha256":"<hex>"}],"needs":"..."}
```

For new integrations, the supported `--handoff-prepare` client validates bounded `agentbroker.handoff.v1` packets with task IDs, states and artifact metadata; see [typed handoff text](agentbroker-client.md#typed-handoff-text). Both formats remain ordinary untrusted message text. The broker neither parses nor enforces this legacy shape. The instructions card described it until 1.4.0, which moved it here to make room for `whoami`. Content larger than a few KiB belongs in files referenced by repository-relative path and SHA-256, never inline past the 16 KiB text limit. A receiver checks each artifact's hash before relying on it.

### Collaboration helper (an agent whose MCP client cannot connect)

`tools/agentbroker/Invoke-AgentBrokerCollaborationMcp.ps1` sends one reviewed JSON request file to the loopback endpoint (validation only without `-Execute`), for an agent whose own MCP client cannot reach the broker, such as Codex under an organization's MCP allowlist. Its addresses are generic `mcp:` mailboxes, with one exception since 1.6.0: `send`'s sender may be the calling Codex agent's own row, `codex:` plus the canonical lowercase GUID in `CODEX_THREAD_ID`. Before sending, the helper reads every `list_sessions` page itself and requires exactly one fresh `codex-native` row with that session ID, the request's broker ID and incarnation, and `Receive` and `WakeIdle`; it refuses when the row is absent, when a second row has the same session ID (on any broker), and when the incarnation is stale, the lease lapsed or the row is observation-only. Replies then wake that native session instead of landing in a mailbox it has to poll.

This is a routing convenience the owner authorised inside the broker's existing local access model, not per-thread authentication. That model is wider than one user: while Allow local connections without a token is on (the default), the loopback endpoint admits any local process of any account, because a loopback connection carries no Windows identity (`WorkerApplication.cs`); turning it off, so callers need the bearer token from the user-scoped control pipe, is what makes it same-user. No trusted per-thread operating-system marker exists, and `CODEX_THREAD_ID` (like `CODEX_SESSION_ID`) is whatever the process running the helper says it is. Everything else is unchanged: recipients stay generic-only, `send_message` stays generic-only, `read_inbox`, `wait_for_messages` and `acknowledge_message` on a native row stay refused, live `reply_to_message` stays refused, and a `claude:` address is never admitted. `wait_for_reply` and `wait_for_receipt` name only a message, and the broker waits as that message's sender, so the helper first reads the original with `get_message_receipt` and refuses the wait unless its sender is a generic mailbox. The request file's bytes reach the broker unchanged, so a retry keeps its `messageId` and sender.

## Claude channel bridge (opt-in)

Claude Code's [channels](https://code.claude.com/docs/en/channels-reference) research preview lets an MCP server push messages into an open interactive session. `AgentBroker.Worker.exe --mcp-channel --data <broker data directory> [--label <text>] [--private]` is such a server, and it is opt-in only: nothing configures it, and the **Connect Claude MCP** button is unchanged.

The bridge registers one generic inbox for its whole lifetime, with one `clientId` and incarnation and the given label (`Claude Code channel` by default), and registers again between waits once 20 seconds have passed, so a worker restart cannot strand it. It waits on the inbox and pushes each new message once as `notifications/claude/channel`. The message text is the tag body. `message_id`, `conversation_id`, `sender_broker`, `sender_session`, `sender_scope` (`local` or `paired`), `expires_at` and, for a reply, `in_reply_to` become tag attributes. Its two tools act on that inbox only:

| Tool | Parameters | Effect |
|---|---|---|
| `acknowledge` | `message_id`, `outcome` (`Delivered` by default, `Held` or `Refused`) | Records the explicit recipient receipt through `acknowledge_message` |
| `reply` | `message_id`, `text`, optional `reply_id` | Answers a message addressed to this inbox through `reply_to_message`; without `reply_id` the ID is derived from the message and the text, so an identical retry returns the same receipt |

A push is not Delivered. Claude Code does not acknowledge a notification, and it drops one silently when the session did not opt the server in, so the receipt stays `Accepted` until the session acknowledges it. Pushes come from the oldest 16 unacknowledged messages, ordered by their creation time, so newer ones wait in the broker until older ones are acknowledged. Before each push the bridge re-reads the owner's choices over the management pipe. A muted inbox is pushed nothing, and its messages wait. A message from a broker that is no longer paired, or from a paired broker to a private inbox, is refused. The bridge never declares `claude/channel/permission`, so no agent that can message the inbox can answer the session's tool-approval prompts. It answers MCP revision 2026-07-28 with 2025-11-25, because Claude Code does not register a channel on the newer revision. Its broker calls appear under Other clients in **MCP client traffic**.

To try it, the person who will watch the session adds the server and starts an interactive CLI session with the development-channel flag:

```powershell
claude mcp add --transport stdio --scope user agentbroker-channel -- "<module folder>\worker\AgentBroker.Worker.exe" --mcp-channel --data "<AgentBroker data directory>"
claude --dangerously-load-development-channels server:agentbroker-channel
```

Accept the development-channel warning, then check that the startup notice names `server:agentbroker-channel`. Channels need claude.ai or Console authentication, and Team and Enterprise organizations must enable them (`channelsEnabled`). Claude Code ignores the development flag with `-p` and through the Agent SDK. The Claude VS Code extension passes `--channels` only, so until this server is on an approved channel allowlist it is a CLI route; see the [compatibility evidence](agentbroker-client-compatibility.md#claude-channels-2026-10-27).

## Delivery contract

A native session receives each peer message as a short preamble plus one JSON object of kind `agentbroker.peer_message` (a delivery notice keeps its own `agentbroker.delivery_notice` envelope): the message and conversation IDs, the reply parent, the exact sender and recipient addresses, `senderLabel`, `senderScope`, when it was sent (`createdAt`), the deadline, the remaining reply budget and the quoted text. `senderLabel` is the label a local sending session registered with, looked up on its exact address when the message is delivered, or `null` once that address is gone. A sender on a paired broker always has a `null` label, because the broker does not fetch the remote directory to deliver. The label is self-declared and identifies or authorizes nothing, and the preamble says so. `senderScope` is `local` for a session on this broker. For one on a paired broker it is `paired broker "<name>" <broker ID>`, where the name is the one that broker advertised when the pairing was approved (its `--name`, by default its machine name). The name is for display only; the broker ID is the one in the sender address. Routing and trust stay with the exact sender address. A native adapter refuses a message whose whole envelope, these fields included, exceeds its limit (32 KiB for Codex); a long label adds up to about 1 KB. These fields were added on 2026-10-28, after a recipient could tell who was asking only by remembering a GUID. `createdAt`, and the preamble's sentences on it (the sender's own timestamp, while delivery follows the order this broker accepted the messages) and on continuing at `remainingReplies` 0, were added on 2026-10-29, after agents on a second workstation reported messages arriving out of order.

One sender's messages to one recipient are delivered in the order the broker accepted them: a newer message waits while an older one for the same pair is still pending but cannot go yet, for example during the 5-second backoff after a deferral, and that older message's expiry ends the wait. Other senders to the same recipient are not held. A Codex chat whose owning view is missing when the broker rediscovers it, before any turn request is written (discovery itself sends only a control frame), defers as `native_owner_unavailable` and is retried, where it used to be refused. An uncertain Codex submission records the library's cause in its reason: `native_uncertain_timeout`, `native_uncertain_native_error`, `native_uncertain_owner_changed` or `native_uncertain_connection`, and `native_submission_uncertain` when none is known. An exception out of a native submission records its cause too: `native_uncertain_raised_io` or `native_uncertain_raised_cancelled` for either client, `native_uncertain_raised_<code>` for a Codex library code, and `native_uncertain_raised_access` for Claude. Any other exception out of a submission, local or forwarded to a paired broker, settles that message `Uncertain` as `submission_failed`, and the next message to that recipient goes as usual. If a delivery or receipt loop itself fails unexpectedly, Status names it (`delivery: loop_failed` or `receipts: loop_failed`, with a count and the time of the last failure) until the worker restarts, and the loop runs again after a pause that starts at one second, doubles after each failure up to a minute, and starts again from one second once the loop has run a minute without failing.

Accepted, submitted, delivered, held, refused, expired, and uncertain are different outcomes. The store persists admission before a delivery attempt. Repeated message IDs with an identical payload recover the existing receipt, after acknowledgement included; conflicting reuse is rejected. `send` compares only caller-supplied fields, so a retry recovers its receipt even when the client regenerated its timestamps. A lapsed generic presence leaves its mailbox reachable (see Mailboxes and retention); a lapsed native session does not. Reply creation is atomic, so concurrent retries preserve the first reply's timestamps and receipt. Expiry bounds a message's delivery window; a retained message can receive a later reply with its own deadline and remaining reply budget. A broker restart invalidates session registrations. An interrupted native submission becomes uncertain rather than blindly replaying a prompt that might already have started a turn.

Queues, session leases, message size, retention, paired brokers, and reply depth are bounded. `tests/Measure-AgentBrokerCoordination.ps1` measures what those bounds cost, one fresh process per sample, interleaved across configurations. Busy, approval-blocked, interrupted, disconnected, and idle states remain distinct. A label match or persisted transcript never proves a session is live or wakeable.

## Identity, privacy, and operating limits

The local HTTP listener binds the literal IPv4 loopback address. It answers two Host authorities, both naming its own port: `127.0.0.1:<port>` and `localhost:<port>`, the second because a managed Claude Code allowlist can admit local MCP servers only as `http://localhost*` URLs. Any other host name, and either name with another port, gets 403. No IPv6 listener is bound: Claude Code 2.1.293 given the localhost URL connected through the IPv4 listener on a workstation that resolves localhost to `::1` first. Optional token authentication is independent of LAN authentication; browser origins and DNS aliases do not inherit local authority. The management interface uses an explicitly user-owned, protected named pipe. Its DACL denies network logons, and clients verify the connected server process and pipe ownership before sending a request. It is never exposed on the LAN listener.

Windows Schannel requires a named private key for TLS. AgentBroker creates a current-user Microsoft Software KSP key with a nonexportable policy. Its encrypted `tls-identity.dat` stores public certificate metadata and the exact owned key name. No raw private-key file, certificate-store installation, administrator action, or OS trust change is required. Identity survives same-user, same-path restarts. Moving the data directory or losing the Windows key fails closed; copying data to another machine is not an identity backup. A new identity requires explicit pairing again.

AgentBroker 1.9.0 renews its five-year TLS certificate at startup when 90 days or less remain. A running worker checks hourly and drains before recreating itself for renewal. The original paired certificate hash stays fixed, and renewed certificates carry a bounded proof tied to its original public key. An upgraded peer can authenticate after missing several renewals. The live certificate must remain valid on the local clock. Owner stop, parent exit, durable failure and cleanup failure prevent renewal from overriding shutdown. The [certificate design and validation record](audits/agentbroker-certificate-continuity-20261107.md) describes the checks.

Upgrade paired brokers to 1.9.0 or later before renewal becomes due. Older workers reject renewed TLS certificates. After the first renewal, the identity metadata uses version 2, which older workers cannot load. Renewal keeps the existing private key; replacing a lost or compromised key still needs explicit identity recovery and pairing.

Pairing shares current and future discoverable sessions directly between the two approved broker identities. Each session can be made private or muted. These choices persist across discovery and restart. A muted session cannot receive automatic peer input. Native client approvals remain authoritative; messages cannot approve tools or elevate either agent's permissions.

The current durable store is intended for low-volume workstation coordination. Defaults bound messages that still carry their text to 4,096, those together with acknowledged-message tombstones to 65,536, raw text to 16 KiB per message, registrations (present or retained) to 256 with at most 64 retained mailboxes, mailbox retention to 24 hours after the owner's last call, paired brokers to 32, pending messages per recipient to 64, a conversation to eight replies, and a blocking wait to 25 seconds with one incoming wait and one receipt wait per exact session and sixteen waits total per worker. Native adapters may impose a smaller envelope limit and explicitly refuse oversized input. Receipts and tombstones remain until message expiry plus one day; reaching capacity refuses new messages rather than silently dropping existing receipts. Each state transition replaces a flushed snapshot, and a message this broker sent that becomes `Delivered` or `Refused` also appends one tombstone line, so the snapshot holds only messages that still have text. The measured costs, before and after tombstones, are recorded in DESIGN-REGISTER (O-agentbroker-02 and `feature/agentbroker-backlog-e`). Idle directory polling does not rewrite durable state.

## Decisions

| Decision | Reason |
| --- | --- |
| Deliver AgentBroker and directly relevant regressions in this effort | The user accepted narrowing the earlier request to clear all 73 unrelated backlog items. |
| Allow one-time setup/restart for explicitly enabled, version-checked adapters | Required for normally opened desktop and VS Code sessions without a stable external submission API. |
| Prefer an existing desktop-owned IPC route over a Codex executable override on Windows | The installed desktop's override changes sandbox/bootstrap initialization. |
| Preserve Claude peer classification | Its exported child token is treated as self-sent and can bypass default inbound mode parity. |
| Do not read native Claude peer key records during source investigation | Live credential access requires a separate exact platform approval under sensitive-file policy H05, and W06 if stored in a workspace. |
| Use a separate self-contained worker for the HTTP server | Keeps the host's runtime requirements and plugin ABI stable. |
| Pair broker identities, including future shared sessions | Matches the requested seamless broker-level authorization. |
| Require both brokers to approve the complete 128-bit comparison code | A discovered name, pairing request or single approval cannot authorize a spoofed peer. |
| Keep native delivery off until explicitly enabled | Version pins and live acceptance are separate from successful generic MCP transport. |
| Treat expiry as a per-message delivery deadline | Long-running tasks can send a fresh reply after the original message's delivery window. |
| Revalidate a paired identity before saving a discovered address change | Restarts and DHCP changes recover without trusting an unverified discovery announcement. |
| Retain unrelated and externally blocked backlog entries | Closing them without implementation or evidence would hide remaining work. |
| Keep a generic MCP mailbox addressable for 24 hours after its owner's last call | Turn-based agents fell off the bus between turns, and a renewal sidecar process was the workaround. Retention is process-local and peers still see presence only, so no federation record or persisted state changed. |
| Never retain a native session | A lapsed native lease means the vendor session is gone; waking a stale native session must stay impossible. |
| Bound blocking waits at 25 seconds, one per class and sixteen total per worker | Stays inside the stdio bridge's 60-second request limit and ordinary client tool timeouts without configuration; each wait occupies a request. |
| Refuse a wait on an unreachable mailbox | An empty result would look like silence forever after a restart; `session_unavailable` tells the agent to register again. |
| Add `send` beside `send_message` | Clients regenerate timestamps on retry; comparing only caller-supplied fields keeps an honest retry from colliding, while `send_message` keeps its exact-record semantics. |
| Publish the protocol as MCP server instructions | Every client receives the same short card in `initialize`, Codex included through the stdio bridge, instead of a per-client setup note. |
| Offer the Claude channel bridge as a separate, hand-configured server | Custom channels are a research preview that needs an interactive per-session development flag and, in Team and Enterprise organizations, an organization switch; wiring it into **Connect Claude MCP** would present it as a supported route. |
| Leave a pushed channel message Accepted until the session acknowledges it | Claude Code never acknowledges a notification and drops it silently when the channel is not registered; only the session's own call is a recipient receipt. |
| Keep a tombstone, not the text, of an acknowledged message this broker sent | Owner decision 2026-10-27: receipts with their text filled the 4,096-message bound at about 1.4 messages a minute. Retries, receipts and replies need only the record, and a separate tombstone file leaves the state a 1.0.4 worker reads unchanged. A paired broker's messages keep their text, because its receipt check compares the whole message. |
